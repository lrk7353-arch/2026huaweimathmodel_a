# 三、我们之前对第一份售卖方案的批评，被正式数据验证了

那份方案把：

> “通过 L1/UB Tensor 联系起来的 Op”

直接作为不可拆的“原子单元”。

我之前就怀疑这样定义会有问题。

正式数据统计以后发现：

### 按它那种“Tensor 共触达”定义：

- **44 / 100** 个 case 直接变成一个大连通块；
- **53 / 100** 的最大块占全部计算 Op 的 90% 以上；
- 最关键的是：

> **没有任何一个 DDR 共享输入跨越这种原子块。**

也就是：

```text
所谓“原子单元”
+
“单元之间共享输入超边”
```

在它自己的定义下，后面的共享输入超图几乎被自己消灭了。

所以我们上一轮指出的逻辑漏洞是成立的。

## 但它的优秀思想可以救回来

只需要把“原子单元”改成：

> **非 COPY producer→consumer DAG 的弱连通分量**

这时候：

- 84 个 case 有多个独立单元；
- **74 / 100 个 case 存在跨单元共享 DDR 输入**；
- 于是共享输入超图真的出现了。

因此正确结构是：

```text
Dependency Components
        ↓
共享 DDR 输入形成 Hyperedge
        ↓
多维超图划分 / 装箱
```

这就非常漂亮了。

# 七、现在我认为三问应该完全分开建模

# 问题一：Task-aware DAG / Hypergraph Partition

P1 最核心的特殊规则是：

> 一个 Subgraph 就是一个 Task。

不同 Task 即使在同一个 Core：

> **缓存也全部清空。**

跨 Task 数据必须走 DDR。fileciteturn0file0L110-L115

所以 P1 真正优化的是：

\[
\boxed{
\text{切图粒度}
+
\text{核分配}
+
\text{Task 顺序}
}
\]

---

## 第一类 case：大量独立 dependency components

这是 100 个 case 的主体。

建立：

### Vertex

每个独立计算分量 \(C_i\)。

权重：

\[
w_i=
(W_i^M,W_i^V,M_i^{L1},M_i^{UB})
\]

### Hyperedge

若多个分量共享一个 DDR 输入 \(t\)：

\[
h_t=\{C_i:t\text{ 被 }C_i\text{ 使用}\}
\]

权重：

\[
s_t
\]

如果该输入被分散到 \(r_t\) 个 Task：

\[
Traffic_t=(r_t-1)s_t
\]

---

然后目标就是：

\[
\min
\left[
\max_k W^M_k,
\max_k W^V_k,
B_{extra},
TaskPenalty
\right]
\]

求解：

> 多级粗化 + 多维 LPT + FM/KL 局部优化。

这里网上第一份方案的思想可以真正发挥作用。

---

## 而且很多这种 case 可以直接尝试：

\[
K=N
\]

也就是：

> 一个 Core 一个大 Subgraph。

因为独立 component 可以自由合并。

这时：

- 同核无需 Task 切换；
- component 内无额外边界；
- 强共享输入 component 可以合并；
- 核间没有 dependency wait；
- 只剩负载均衡。

这解释了为什么刚才 case001 能做到：

\[
4.907\times
\]

所以第二个视频博主说的：

> `K ≈ N`

**并不是完全错误。**

正确说法应该是：

> 对“独立 component 丰富”的图，K=N 极可能是非常强的方案；但不能推广到所有图。

# 八、P1 真正难的是剩下那一小批“大连通 DAG”

正式数据里只有 16 个 case 是纯单连通，约 20 个是一个大块占绝对主体。

这些才是 P1 真正值得研究的部分。

比如有的：

```text

每层宽度约 12
```

有的则是：

```text
19636 Op
仅约 28 层
最大一层 2181 个 Op
```

两者显然不能使用同一种切法。

---

我建议这里做第二层结构分解：

### ① Critical Path

求：

\[
rank_f(v),\quad rank_b(v)
\]

定义：

\[
slack(v)=CP-rank_f(v)-rank_b(v)
\]

避免在高 criticality 区域产生高成本跨核切分。

这个就是第二个视频做得好的地方。

---

### ② Fork-Join / Parallel Region 检测

识别：

```text
       ┌ Branch A ┐
Fork ──┼ Branch B ┼── Join
       └ Branch C ┘
```

这种地方才是真正应该多核展开的地方。

可以采用：

- dominator / post-dominator；
- forward/backward depth；
- frontier；
- 小割集；
- DAG separator。

---

### ③ DAG-convex partition

这里有一个非常容易踩的坑：

> 随便把 DAG 里的节点 merge，会让“子图 DAG”产生环。

我刚才做原型时甚至亲手触发了一次官方：

```text
contracted subgraph graph contains a cycle
```

所以最终算法必须明确加入：

# **Acyclic contraction constraint**

也就是每次：

```text
merge / move / split
```

都必须保证 quotient graph 仍是 DAG。

这是一个很好的论文建模点。

# 十一、P2 我会采用“HEFT + Hypergraph FM”两层求解

### 第一层：Communication-aware HEFT

按照 upward rank：

\[
rank_u(v)
=
w(v)+
\max_{u\in succ(v)}
(c(v,u)+rank_u(u))
\]

然后每个 Op 选择使 Estimated Finish Time 最小的 Core：

\[
core^*(v)=
\arg\min_k EFT(v,k)
\]

这里 EFT 同时考虑：

- PIPE_M / PIPE_V 当前负载；
- predecessor finish；
- 500 cycles；
- Tensor 搬运；
- 共享输入复制。

---

### 第二层：FM / Local refinement

允许：

```text
move(v, coreA → coreB)
swap(v,u)
move(branch)
```

delta score 同时计算：

- Compute imbalance；
- Input replication；
- Cross-core intermediate traffic；
- Critical path；
- spill risk。

- FIFO；
- hit 不刷新 FIFO。fileciteturn0file0L400-L408

## 我对正式数据又做了统计

所有原始输入 Tensor：

> **没有任何一个单 Tensor 大于 1 MB。**

最大单个大约：

\[
295KB
\]

所以全部都可缓存。

而且：

> **50 / 100 个 case 的全部原始 COPY_IN 总量本身都不超过 1 MB。**

也就是说 P3 并不是一个装饰性问题。

L2 在相当多 case 里理论上有非常强的发挥空间。

# 十四、P3 的真正创新：Leader–Follower Cache Scheduling

网上第一份方案的问题是：

> 让多个 Core 同波次读取同一个 Tensor。

但这会：

```text
Core0 发 COPY_IN(X) → miss
Core1 同时发 COPY_IN(X) → 还是 miss
```

因为第一个还没搬完。

---

我们应该做：

```text
Core 0:
    COPY_IN(X) MISS
    ────────────────完成
                    ↓ L2 insert

Core 1:
                       COPY_IN(X) HIT

Core 2:
                            COPY_IN(X) HIT
```

所以条件应该是：

\[
t_{\text{leader finish}}
<
t_{\text{follower issue}}
<
t_{\text{FIFO eviction}}
\]

而不是“同时”。

---

## 可以定义 Cache reuse distance

若 leader 插入 Tensor \(x\) 后，到 follower 再访问之间，新插入缓存的数据总量为：

\[
D_x=
\sum_{\tau\in \text{between}} size(\tau)
\]

若：

\[
D_x<1MB
\]

则大概率保持命中。

于是 P3 变成：

# **Core Partition + Cache-aware Topological Ordering**

这非常有论文价值。

\[

这个论文故事就很完整。

### 2. `bl/tl/slack` 关键路径分析是一个不错的启发式特征

它把 DAG 做成：

\[

- 关键路径上的 cut 应该慎重；

\]

之后用

\[
\frac{Makespan}{LB}
\]

判断解离理论极限还有多远。

- 解释为什么加速比饱和；

# 2. 它的 Makespan 算法和官方 Makespan 根本不是一回事

视频代码核心逻辑基本是：

```text
拓扑取一个节点
→ 找当前负载最小的核

```

例如它展示：

```text

Core1 = 60
Core2 = 90
Core3 = 45

但官方 evaluator 的 Makespan 包含：

- PIPE_M；
- PIPE_V；
- MTE2；
- MTE3；
- Pipe 内串行、Pipe 间并行；
- COPY；
- DDR 60 B/cycle 共享；
- 多核并发带宽争用；
- Task activation；
- 100 / 1000 / 500 cycles 同步；
- L1/UB spill；
- 跨核 COPY。

官方甚至是离散事件模拟。fileciteturn0file0L368-L383

所以：

> **`max(sum cycles per core)` 不能作为这道题真正的 Makespan。**

最多是 surrogate。

# 4. `K=N` 被它说得太绝对了

它最后给出的结论类似：

> 场景 A 中，`K=N` 是最优选择。

理由是：

- 每核一个子图；
- 避免同核 Task 切换的 100 cycles；
- 减少边界搬运。

这个方向有道理，但**不能推出 K=N 普遍最优**。

官方明确指出：

> 切得太少会压缩并行空间、增加缓存压力；切得太多则增加通信。fileciteturn0file0L65-L71

例如 4 核：

```text
K = 4
```

意味着只有 4 个大调度单元。

如果其中一个子图特别重：

```text
[100, 100, 100, 500]
```

一个核就会成为长尾。

此时切成：

```text
K = 6 或 K = 8
```

虽然增加 Task 开销，却可能明显改善负载均衡。

所以真正应该研究的是：

\[
K^*
=
f(\text{graph structure},
\text{cut traffic},
\text{load balance},
\text{spill})
\]

而不是固定：

\[
K=N
\]

这一点上一份售卖方案的“粒度扫描”反而更成熟。

---

# 5. 它的关键路径并不是“真实执行关键路径”

这个视频的 CP 是根据算子 cycles 建出来的。

但官方实际执行中，一个路径可能是：

```text
计算
→ COPY_OUT
→ DDR竞争
→ 1000 cycles同步
→ COPY_IN
→ 等Pipe
→ 计算
```

因此官方运行时的 critical path 是动态的。

所以 `slack=0` 很有价值，但应该理解成：

> **计算 DAG 的静态关键性特征**

而不能把它理解成：

> evaluator 中真正决定 Makespan 的关键路径。

否则可能出现一个静态非关键节点，因为 DDR 拥塞变成运行时 bottleneck。

---

# 6. 它的目标函数也需要修改

视频写：

\[
F= Makespan+\gamma\frac{\Delta Traffic}{BW}
\]

这个形式论文看起来舒服，但实战不够严谨。

因为官方的 Makespan 本身已经包含：

> DDR 数据量增加 → 带宽争用增加 → 时间变长。

因此再加：

\[
\Delta Traffic/BW
\]

一定程度存在**重复计罚**。

更重要的是官方定义非常明确：

> Makespan 是最重要指标，额外搬运是次要指标。fileciteturn0file0L85-L106

所以我更倾向于：

\[
\min Makespan
\]

优先，然后：

\[
\min AddedTraffic
\]

作为 secondary objective。

或者 surrogate 搜索时才使用加权函数。

# 二、最大的问题：问题一开头的“原子单元”可能把整个题直接做废

它第一步定义：

> 删除 COPY_IN / COPY_OUT 和 DDR Tensor，把核内操作按照 L1/UB Tensor 的连接关系划成连通分量，并把这些连通分量作为原子单元。fileciteturn0file1L6-L16

然后它认为不同“原子单元”之间没有依赖，因此把问题降维为：

> 带共享输入复用的并行划分。

这个说法看起来很漂亮，但我认为这里存在一个**非常危险的逻辑问题**。

---

## 举个最简单的例子

原图：

```text
DDR input
    ↓
COPY_IN
    ↓
 L1 tensor
   ↙   ↘
 Op A  Op B
```

你把 DDR tensor 和 COPY_IN 删除以后：

```text
 L1 tensor
   ↙   ↘
 Op A  Op B
```

A 和 B **依然在同一个连通分量里**。

也就是说：

> 如果多个计算共享同一个 COPY_IN 得到的核内 tensor，它们本来就会因为这个 L1/UB tensor 被划进同一个连通分量。

而官方还特别规定：

> 每个 DDR 输入只搬入一次；中间计算不与 DDR 交换数据。fileciteturn0file0L245-L253

所以这会产生一个非常值得警惕的问题：

### 它所谓“不同原子单元之间共享 DDR 输入”的超边，到底有多少？

很可能：

> **非常少，甚至根本不存在。**

如果如此，那么它后面大篇幅建立的

\[
\text{shared-input hypergraph}
\]

在“原子单元”这一层可能直接退化。

---

## 更严重的是：一个大计算图可能只有一个连通分量

假如一个测试用例的主要神经网络计算 DAG 本身就是连通的，那么按照它的定义：

```text
整个图
 ↓
一个原子单元
```

如果把这个“原子单元”当不可再拆的单位，那么：

```text
1 个单元
→ 只能丢到 1 个核
→ 另外 4 个核看戏
```

多核调度直接失去意义。

而官方明明要求的是：

> 给**每个非 COPY 操作**分配 subgraph id。fileciteturn0file0L127-L144

也就是说真正的搜索空间恰恰在：

> **一个连通 DAG 内部到底在哪里切。**

这份方案第一步反而很可能把最重要的搜索空间先消灭了。

---

### 所以这个“原子单元”最多只能用来：

> 做图结构诊断 / coarse initialization，

而不能默认作为：

> **不可拆的最小调度单位。**

这是我认为这份方案目前最大的隐患。

---

# 三、问题一对“额外搬运”的定义少了一大块

这份方案写道：

> 场景 A 下额外搬运量仅有两项：
>
> 1. 相同 DDR 输入被多个子图重复 COPY_IN；
> 2. 大子图引起 step2 换入换出。fileciteturn0file1L39-L45

这里明显不完整。

官方非常明确地写了三类：

> 新增搬运主要来自：
>
> 1. **跨 Task 边界数据**
> 2. 多个 Task 对同一输入重复读取
> 3. L1/UB 容量不足导致的换出换入。fileciteturn0file0L99-L105

第一项非常关键：

```text
Op A
 ↓
Tensor T
 ↓
Op B
```

如果 A、B 被切进不同 subgraph：

```text
Subgraph 1
   Op A
    ↓
COPY_OUT
    ↓
   DDR
    ↓
COPY_IN
    ↓
Subgraph 2
   Op B
```

这个 `Tensor T` 的跨子图通信本身就是额外 DDR 流量。

而且在场景 A：

> 即使两个 Task 在同一个 Core 上，缓存也会清空，照样需要 DDR。fileciteturn0file0L110-L115

所以问题一真正重要的 cut penalty 应该至少包括：

\[
C_{\text{cut}}
=
C_{\text{intermediate-boundary}}
+
C_{\text{repeated-input}}
+
C_{\text{spill}}
\]

而这份方案主要盯着第二项。

### 这不是小修小补，而会直接改变最优切图位置。

---

# 四、它对场景 A 的“同核排序”也有一点概念混淆

它写：

> 同核按照共享输入相邻排列，以便同一子图内 COPY_IN 复用。fileciteturn0file1L72-L84

这里需要严格区分两个概念：

### 如果已经是不同 subgraph：

在场景 A：

```text
Task 1结束
→ 清空缓存
→ Task 2开始
```

因此：

> Task 1 和 Task 2 挨得再近，也不能复用 L1/UB。

官方对此说得非常清楚。fileciteturn0file0L110-L115

所以：

**“相邻排序”本身并不能产生 COPY_IN 复用。**

真正能减少重复 COPY_IN 的是：

> 把它们合进**同一个 subgraph / Task**。

顺序主要能够影响：

- DDR 并发竞争；
- 各核执行时间重叠；
- 前驱等待；
- Pipe 时间错峰。

这两件事情不能混为一谈。

# 五、问题二里面有一个很明显的“理论断言过头”

它写：

> 理论上问题二的加速比应该处处不低于问题一，可以作为正确性检验。fileciteturn0file1L169-L175

这个我认为**不能成立为必然结论**。

因为场景 B 虽然有优势：

> 同核数据可以驻留，不必 DDR 中转。

但题目同时明确提醒：

> 驻留数据会持续占用核内缓存，压缩后续子图空间，并可能降低执行效率。fileciteturn0file0L116-L120

官方甚至单独强调：

> 场景 B 中跨多个子图的数据驻留会占缓存，因此可能降低单个子图调度效率。fileciteturn0file0L197-L199

问题一反而可以利用 Task 边界“清缓存”。

因此完全可能出现：

```text
A：
多 Task
虽然有通信
但每个 Task 缓存压力小

B：
一个巨大 Task
通信少
但大量 tensor 长时间驻留
→ step2 spill
→ 调度恶化
```

所以：

> `Makespan_B <= Makespan_A`

不是数学上的必然性质。

拿这个当“模型正确性检验”是危险的。

# 六、最严重的第二个问题：问题三“同波次访问”可能恰好会让 Cache 全部 miss

这是我看这 6 页时觉得**最有意思、也最致命**的地方。

它的想法是：

> 同一个共享输入的数据，在多个核之间安排到“同一波次”，让访问靠得很近，以提高 Cache 命中。fileciteturn0file1L218-L237

直觉上没问题。

但是看看官方 Cache 真正如何工作。

官方规定：

> COPY_IN **发射时**查询 Cache；
>
> 如果 miss，就去 DDR；
>
> **DDR 搬运完成以后才写入 Cache**。fileciteturn0file0L400-L408

这非常重要。

---

假设两个核同时读取 tensor X：

```text
t = 100

Core 0: COPY_IN(X)
Core 1: COPY_IN(X)
```

Core 0 发射时：

```text
Cache 没 X
→ MISS
→ DDR
```

Core 1 几乎同时发射：

```text
Cache 还是没 X
→ MISS
→ DDR
```

因为：

> Core 0 的 X **还没搬完，也还没写入 Cache**。

结果：

```text
两核同时 MISS
```

而不是：

```text
一核 MISS
另一核 HIT
```

---

## 真正 Cache-friendly 的策略反而应该类似：

```text
Core 0:
COPY_IN(X)
──────完成──────>
       ↓ 写入 L2

Core 1:
          COPY_IN(X)
          ↓
         HIT
```

也就是说应该是：

# **近，但不能太近。**

更加准确地说是：

> **first-loader / leader miss + delayed followers**

要求 follower 的 COPY_IN：

\[
t_{\text{follower}}
>
t_{\text{leader finish}}
\]

同时还必须：

\[
t_{\text{follower}}
<
t_{\text{eviction}}
\]

所以真正要控制的是：

\[
t_{\text{load-complete}}
<
t_{\text{reuse}}
<
t_{\text{FIFO-evict}}
\]

而不是简单的：

\[
\phi(u)=\phi(v)
\]

“同波次”。

这一点如果不改，问题三甚至可能出现：

> 越努力让共享访问同步，Cache hit rate 反而越低。

这是一个非常值得我们后续利用的突破口。

---

# 七、它的 FIFO 模型还是稍微过于理想化

它用了：

\[
\sum size < 1MB
\]

之类的“波次工作集”来近似 Cache 是否能命中。fileciteturn0file1L231-L245

作为解析模型可以。

但真实 evaluator 是：

```text
FIFO
+
miss completion 后插入
+
hit 不改变 FIFO 顺序
+
多核同时共享带宽
+
并发 miss 完成时间不同
```

官方明确说明：

> 命中不会改变 FIFO 顺序；miss 完成后才插入；容量不足时按 FIFO 淘汰。fileciteturn0file0L400-L408

因此 Cache 状态其实是一个**事件驱动系统**。

只用：

```text
波次总量 < 1MB
```

无法准确推断 hit。

最终最好还是：

> 用官方 evaluator / 仿 evaluator 做 simulation-in-the-loop。

## 一个非常关键的新发现：绝大多数图天然存在大量“独立计算块”

我重新定义了一个比网上第一份方案更合理的结构：

# 三、我们之前对第一份售卖方案的批评，被正式数据验证了

那份方案把：

> “通过 L1/UB Tensor 联系起来的 Op”

直接作为不可拆的“原子单元”。

我之前就怀疑这样定义会有问题。

正式数据统计以后发现：

### 按它那种“Tensor 共触达”定义：

- **44 / 100** 个 case 直接变成一个大连通块；
- **53 / 100** 的最大块占全部计算 Op 的 90% 以上；
- 最关键的是：

> **没有任何一个 DDR 共享输入跨越这种原子块。**

也就是：

```text
所谓“原子单元”
+
“单元之间共享输入超边”
```

在它自己的定义下，后面的共享输入超图几乎被自己消灭了。

所以我们上一轮指出的逻辑漏洞是成立的。

---

## 但它的优秀思想可以救回来

只需要把“原子单元”改成：

> **非 COPY producer→consumer DAG 的弱连通分量**

这时候：

- 84 个 case 有多个独立单元；
- **74 / 100 个 case 存在跨单元共享 DDR 输入**；
- 于是共享输入超图真的出现了。

因此正确结构是：

```text
Dependency Components
        ↓
共享 DDR 输入形成 Hyperedge
        ↓
多维超图划分 / 装箱
```

这就非常漂亮了。

# 七、现在我认为三问应该完全分开建模

这是我们最终框架的核心。

# 问题一：Task-aware DAG / Hypergraph Partition

P1 最核心的特殊规则是：

> 一个 Subgraph 就是一个 Task。

不同 Task 即使在同一个 Core：

> **缓存也全部清空。**

跨 Task 数据必须走 DDR。fileciteturn0file0L110-L115

所以 P1 真正优化的是：

\[
\boxed{
\text{切图粒度}
+
\text{核分配}
+
\text{Task 顺序}
}
\]

---

## 第一类 case：大量独立 dependency components

这是 100 个 case 的主体。

建立：

### Vertex

每个独立计算分量 \(C_i\)。

权重：

\[
w_i=
(W_i^M,W_i^V,M_i^{L1},M_i^{UB})
\]

### Hyperedge

若多个分量共享一个 DDR 输入 \(t\)：

\[
h_t=\{C_i:t\text{ 被 }C_i\text{ 使用}\}
\]

权重：

\[
s_t
\]

如果该输入被分散到 \(r_t\) 个 Task：

\[
Traffic_t=(r_t-1)s_t
\]

---

然后目标就是：

\[
\min
\left[
\max_k W^M_k,
\max_k W^V_k,
B_{extra},
TaskPenalty
\right]
\]

求解：

> 多级粗化 + 多维 LPT + FM/KL 局部优化。

这里网上第一份方案的思想可以真正发挥作用。

---

## 而且很多这种 case 可以直接尝试：

\[
K=N
\]

也就是：

> 一个 Core 一个大 Subgraph。

因为独立 component 可以自由合并。

这时：

- 同核无需 Task 切换；
- component 内无额外边界；
- 强共享输入 component 可以合并；
- 核间没有 dependency wait；
- 只剩负载均衡。

这解释了为什么刚才 case001 能做到：

\[
4.907\times
\]

所以第二个视频博主说的：

> `K ≈ N`

**并不是完全错误。**

正确说法应该是：

> 对“独立 component 丰富”的图，K=N 极可能是非常强的方案；但不能推广到所有图。

# 八、P1 真正难的是剩下那一小批“大连通 DAG”

正式数据里只有 16 个 case 是纯单连通，约 20 个是一个大块占绝对主体。

这些才是 P1 真正值得研究的部分。

比如有的：

```text
17995 Op
2440 层
每层宽度约 12
```

有的则是：

```text
19636 Op
仅约 28 层
最大一层 2181 个 Op
```

两者显然不能使用同一种切法。

---

我建议这里做第二层结构分解：

### ① Critical Path

求：

\[
rank_f(v),\quad rank_b(v)
\]

定义：

\[
slack(v)=CP-rank_f(v)-rank_b(v)
\]

避免在高 criticality 区域产生高成本跨核切分。

这个就是第二个视频做得好的地方。

---

### ② Fork-Join / Parallel Region 检测

识别：

```text
       ┌ Branch A ┐
Fork ──┼ Branch B ┼── Join
       └ Branch C ┘
```

这种地方才是真正应该多核展开的地方。

可以采用：

- dominator / post-dominator；
- forward/backward depth；
- frontier；
- 小割集；
- DAG separator。

---

### ③ DAG-convex partition

这里有一个非常容易踩的坑：

> 随便把 DAG 里的节点 merge，会让“子图 DAG”产生环。

我刚才做原型时甚至亲手触发了一次官方：

```text
contracted subgraph graph contains a cycle
```

所以最终算法必须明确加入：

# **Acyclic contraction constraint**

也就是每次：

```text
merge / move / split
```

都必须保证 quotient graph 仍是 DAG。

这是一个很好的论文建模点。

# 十一、P2 我会采用“HEFT + Hypergraph FM”两层求解

### 第一层：Communication-aware HEFT

按照 upward rank：

\[
rank_u(v)
=
w(v)+
\max_{u\in succ(v)}
(c(v,u)+rank_u(u))
\]

然后每个 Op 选择使 Estimated Finish Time 最小的 Core：

\[
core^*(v)=
\arg\min_k EFT(v,k)
\]

这里 EFT 同时考虑：

- PIPE_M / PIPE_V 当前负载；
- predecessor finish；
- 500 cycles；
- Tensor 搬运；
- 共享输入复制。

---

### 第二层：FM / Local refinement

允许：

```text
move(v, coreA → coreB)
swap(v,u)
move(branch)
```

delta score 同时计算：

- Compute imbalance；
- Input replication；
- Cross-core intermediate traffic；
- Critical path；
- spill risk。

# 十三、问题三现在我认为反而有一个很漂亮的创新点

P3 是 P2 + 1 MB FIFO L2。

官方规则：

- miss → DDR；
- **miss 完成后才写 Cache**；
- hit → 独立 250 B/cycle Cache 带宽；
- FIFO；
- hit 不刷新 FIFO。fileciteturn0file0L400-L408

## 我对正式数据又做了统计

所有原始输入 Tensor：

> **没有任何一个单 Tensor 大于 1 MB。**

最大单个大约：

\[
295KB
\]

所以全部都可缓存。

而且：

> **50 / 100 个 case 的全部原始 COPY_IN 总量本身都不超过 1 MB。**

也就是说 P3 并不是一个装饰性问题。

L2 在相当多 case 里理论上有非常强的发挥空间。

# 十四、P3 的真正创新：Leader–Follower Cache Scheduling

网上第一份方案的问题是：

> 让多个 Core 同波次读取同一个 Tensor。

但这会：

```text
Core0 发 COPY_IN(X) → miss
Core1 同时发 COPY_IN(X) → 还是 miss
```

因为第一个还没搬完。

---

我们应该做：

```text
Core 0:
    COPY_IN(X) MISS
    ────────────────完成
                    ↓ L2 insert

Core 1:
                       COPY_IN(X) HIT

Core 2:
                            COPY_IN(X) HIT
```

所以条件应该是：

\[
t_{\text{leader finish}}
<
t_{\text{follower issue}}
<
t_{\text{FIFO eviction}}
\]

而不是“同时”。

---

## 可以定义 Cache reuse distance

若 leader 插入 Tensor \(x\) 后，到 follower 再访问之间，新插入缓存的数据总量为：

\[
D_x=
\sum_{\tau\in \text{between}} size(\tau)
\]

若：

\[
D_x<1MB
\]

则大概率保持命中。

于是 P3 变成：

# **Core Partition + Cache-aware Topological Ordering**

这非常有论文价值。

\frac{Makespan}{LB}
\]

# 2. 它的 Makespan 算法和官方 Makespan 根本不是一回事

- PIPE_M；
- PIPE_V；
- MTE2；

- COPY；
- DDR 60 B/cycle 共享；
- 多核并发带宽争用；
- Task activation；
- 100 / 1000 / 500 cycles 同步；
- L1/UB spill；
- 跨核 COPY。

官方甚至是离散事件模拟。fileciteturn0file0L368-L383

所以：

# 4. `K=N` 被它说得太绝对了

它最后给出的结论类似：

> 场景 A 中，`K=N` 是最优选择。

理由是：

- 每核一个子图；
- 避免同核 Task 切换的 100 cycles；
- 减少边界搬运。

这个方向有道理，但**不能推出 K=N 普遍最优**。

官方明确指出：

> 切得太少会压缩并行空间、增加缓存压力；切得太多则增加通信。fileciteturn0file0L65-L71

例如 4 核：

```text
K = 4
```

意味着只有 4 个大调度单元。

如果其中一个子图特别重：

```text
[100, 100, 100, 500]
```

一个核就会成为长尾。

此时切成：

```text
K = 6 或 K = 8
```

虽然增加 Task 开销，却可能明显改善负载均衡。

所以真正应该研究的是：

\[
K^*
=
f(\text{graph structure},
\text{cut traffic},
\text{load balance},
\text{spill})
\]

而不是固定：

\[
K=N
\]

这一点上一份售卖方案的“粒度扫描”反而更成熟。

# 5. 它的关键路径并不是“真实执行关键路径”

这个视频的 CP 是根据算子 cycles 建出来的。

但官方实际执行中，一个路径可能是：

```text
计算
→ COPY_OUT
→ DDR竞争
→ 1000 cycles同步
→ COPY_IN
→ 等Pipe
→ 计算
```

因此官方运行时的 critical path 是动态的。

所以 `slack=0` 很有价值，但应该理解成：

> **计算 DAG 的静态关键性特征**

而不能把它理解成：

> evaluator 中真正决定 Makespan 的关键路径。

否则可能出现一个静态非关键节点，因为 DDR 拥塞变成运行时 bottleneck。

---

# 6. 它的目标函数也需要修改

视频写：

\[
F= Makespan+\gamma\frac{\Delta Traffic}{BW}
\]

这个形式论文看起来舒服，但实战不够严谨。

因为官方的 Makespan 本身已经包含：

> DDR 数据量增加 → 带宽争用增加 → 时间变长。

因此再加：

\[
\Delta Traffic/BW
\]

一定程度存在**重复计罚**。

更重要的是官方定义非常明确：

> Makespan 是最重要指标，额外搬运是次要指标。fileciteturn0file0L85-L106

所以我更倾向于：

\[
\min Makespan
\]

优先，然后：

\[
\min AddedTraffic
\]

作为 secondary objective。

或者 surrogate 搜索时才使用加权函数。

这份思路**不是胡写的**，而且有几处抓到了 A 题真正的关键：**图划分、负载均衡、DDR 带宽、缓存驻留、共享输入复用、L2 FIFO Cache**。作为比赛开始几小时内整理出的“理论框架”，完成度相当高。

但如果问：

> **能不能直接照这个思路做，指望跑出很强的结果？**

我的判断是：**风险很大。**

最值得警惕的不是“算法不够高级”，而是里面至少有 **4 个与官方评估器机制直接冲突或过度简化的地方**。其中**问题 1 的“原子单元”定义**和**问题 3 的“同波次 Cache 命中”策略**尤其严重。

我甚至会把它评价成：

> **论文叙事框架：8/10**  
> **对题意的总体理解：7/10**  
> **与官方 evaluator 的严格一致性：5/10**  
> **直接拿去写代码跑分：目前最多 5～6/10**

# 一、它最值得肯定的几个地方

### 1. 它意识到了这不是普通 DAG 调度，而是“切图 + 分核 + 核内排序”联合优化

这是对的。

官方自己明确说，三个决策高度耦合：

- 切图；
- 核心分配；
- 同核子图执行顺序。

而且切得太碎会增加 DDR 通信，切得太粗又损失并行度和增加缓存压力。fileciteturn0file0L65-L76

这份方案没有简单搞个拓扑排序 + LPT，而是试图同时考虑：

> 超图划分 → 多维负载均衡 → 粒度控制 → 顺序优化。

这个大框架是合理的。

---

### 2. 用 Cube / Vector 双维负载，而不是一个简单的 `cycles`

这点很好。

题目明确说 Cube 和 Vector 可以并行，不同 Pipe 也可以并行。fileciteturn0file0L206-L210

它因此没有只用

\[
load_i=\sum cycles
\]

而是考虑类似

\[
(W_M,W_V)
\]

再做双维平衡。fileciteturn0file1L63-L71

这比很多“普通多机调度模型”明显更贴题。

---

### 3. 问题 2 抓到了 sgid 在场景 B 中角色发生变化

这其实是这份方案中我比较喜欢的一点。

它指出：

> 场景 B 中，同核全部子图会组成一个 Task，因此 sgid 不再主要决定通信边界，而更多控制核内调度顺序和缓存活跃集。fileciteturn0file1L95-L103

这个认识和官方机制确实吻合。

官方也写了：问题 2、3 中，同一核心的全部子图会合并为一个 Task；同核依赖保留在核内，不插入边界 COPY。fileciteturn0file0L385-L388

所以问题二确实不能简单复制问题一。

---

### 4. 问题 3 意识到了 FIFO Cache 不能只看容量，还要看 reuse distance

这个方向是对的。

它开始讨论：

> FIFO、复用距离、共享输入的访问时序。fileciteturn0file1L204-L227

这比简单说“L2 有 1 MB，所以共享数据小于 1 MB 就能命中”强得多。

但是——

它后面设计的“同波次”策略，恰恰又出现了一个非常严重的问题。

后面说。

# 二、最大的问题：问题一开头的“原子单元”可能把整个题直接做废

它第一步定义：

> 删除 COPY_IN / COPY_OUT 和 DDR Tensor，把核内操作按照 L1/UB Tensor 的连接关系划成连通分量，并把这些连通分量作为原子单元。fileciteturn0file1L6-L16

然后它认为不同“原子单元”之间没有依赖，因此把问题降维为：

> 带共享输入复用的并行划分。

这个说法看起来很漂亮，但我认为这里存在一个**非常危险的逻辑问题**。

---

## 举个最简单的例子

原图：

```text
DDR input
    ↓
COPY_IN
    ↓
 L1 tensor
   ↙   ↘
 Op A  Op B
```

你把 DDR tensor 和 COPY_IN 删除以后：

```text
 L1 tensor
   ↙   ↘
 Op A  Op B
```

A 和 B **依然在同一个连通分量里**。

也就是说：

> 如果多个计算共享同一个 COPY_IN 得到的核内 tensor，它们本来就会因为这个 L1/UB tensor 被划进同一个连通分量。

而官方还特别规定：

> 每个 DDR 输入只搬入一次；中间计算不与 DDR 交换数据。fileciteturn0file0L245-L253

所以这会产生一个非常值得警惕的问题：

### 它所谓“不同原子单元之间共享 DDR 输入”的超边，到底有多少？

很可能：

> **非常少，甚至根本不存在。**

如果如此，那么它后面大篇幅建立的

\[
\text{shared-input hypergraph}
\]

在“原子单元”这一层可能直接退化。

---

## 更严重的是：一个大计算图可能只有一个连通分量

假如一个测试用例的主要神经网络计算 DAG 本身就是连通的，那么按照它的定义：

```text
整个图
 ↓
一个原子单元
```

如果把这个“原子单元”当不可再拆的单位，那么：

```text
1 个单元
→ 只能丢到 1 个核
→ 另外 4 个核看戏
```

多核调度直接失去意义。

而官方明明要求的是：

> 给**每个非 COPY 操作**分配 subgraph id。fileciteturn0file0L127-L144

也就是说真正的搜索空间恰恰在：

> **一个连通 DAG 内部到底在哪里切。**

这份方案第一步反而很可能把最重要的搜索空间先消灭了。

---

### 所以这个“原子单元”最多只能用来：

> 做图结构诊断 / coarse initialization，

而不能默认作为：

> **不可拆的最小调度单位。**

这是我认为这份方案目前最大的隐患。

---

# 三、问题一对“额外搬运”的定义少了一大块

这份方案写道：

> 场景 A 下额外搬运量仅有两项：
>
> 1. 相同 DDR 输入被多个子图重复 COPY_IN；
> 2. 大子图引起 step2 换入换出。fileciteturn0file1L39-L45

这里明显不完整。

官方非常明确地写了三类：

> 新增搬运主要来自：
>
> 1. **跨 Task 边界数据**
> 2. 多个 Task 对同一输入重复读取
> 3. L1/UB 容量不足导致的换出换入。fileciteturn0file0L99-L105

第一项非常关键：

```text
Op A
 ↓
Tensor T
 ↓
Op B
```

如果 A、B 被切进不同 subgraph：

```text
Subgraph 1
   Op A
    ↓
COPY_OUT
    ↓
   DDR
    ↓
COPY_IN
    ↓
Subgraph 2
   Op B
```

这个 `Tensor T` 的跨子图通信本身就是额外 DDR 流量。

而且在场景 A：

> 即使两个 Task 在同一个 Core 上，缓存也会清空，照样需要 DDR。fileciteturn0file0L110-L115

所以问题一真正重要的 cut penalty 应该至少包括：

\[
C_{\text{cut}}
=
C_{\text{intermediate-boundary}}
+
C_{\text{repeated-input}}
+
C_{\text{spill}}
\]

而这份方案主要盯着第二项。

### 这不是小修小补，而会直接改变最优切图位置。

---

# 四、它对场景 A 的“同核排序”也有一点概念混淆

它写：

> 同核按照共享输入相邻排列，以便同一子图内 COPY_IN 复用。fileciteturn0file1L72-L84

这里需要严格区分两个概念：

### 如果已经是不同 subgraph：

在场景 A：

```text
Task 1结束
→ 清空缓存
→ Task 2开始
```

因此：

> Task 1 和 Task 2 挨得再近，也不能复用 L1/UB。

官方对此说得非常清楚。fileciteturn0file0L110-L115

所以：

**“相邻排序”本身并不能产生 COPY_IN 复用。**

真正能减少重复 COPY_IN 的是：

> 把它们合进**同一个 subgraph / Task**。

顺序主要能够影响：

- DDR 并发竞争；
- 各核执行时间重叠；
- 前驱等待；
- Pipe 时间错峰。

这两件事情不能混为一谈。

---

# 五、问题二里面有一个很明显的“理论断言过头”

它写：

> 理论上问题二的加速比应该处处不低于问题一，可以作为正确性检验。fileciteturn0file1L169-L175

这个我认为**不能成立为必然结论**。

因为场景 B 虽然有优势：

> 同核数据可以驻留，不必 DDR 中转。

但题目同时明确提醒：

> 驻留数据会持续占用核内缓存，压缩后续子图空间，并可能降低执行效率。fileciteturn0file0L116-L120

官方甚至单独强调：

> 场景 B 中跨多个子图的数据驻留会占缓存，因此可能降低单个子图调度效率。fileciteturn0file0L197-L199

问题一反而可以利用 Task 边界“清缓存”。

因此完全可能出现：

```text
A：
多 Task
虽然有通信
但每个 Task 缓存压力小

B：
一个巨大 Task
通信少
但大量 tensor 长时间驻留
→ step2 spill
→ 调度恶化
```

所以：

> `Makespan_B <= Makespan_A`

不是数学上的必然性质。

拿这个当“模型正确性检验”是危险的。

---

# 六、最严重的第二个问题：问题三“同波次访问”可能恰好会让 Cache 全部 miss

这是我看这 6 页时觉得**最有意思、也最致命**的地方。

它的想法是：

> 同一个共享输入的数据，在多个核之间安排到“同一波次”，让访问靠得很近，以提高 Cache 命中。fileciteturn0file1L218-L237

直觉上没问题。

但是看看官方 Cache 真正如何工作。

官方规定：

> COPY_IN **发射时**查询 Cache；
>
> 如果 miss，就去 DDR；
>
> **DDR 搬运完成以后才写入 Cache**。fileciteturn0file0L400-L408

这非常重要。

---

假设两个核同时读取 tensor X：

```text
t = 100

Core 0: COPY_IN(X)
Core 1: COPY_IN(X)
```

Core 0 发射时：

```text
Cache 没 X
→ MISS
→ DDR
```

Core 1 几乎同时发射：

```text
Cache 还是没 X
→ MISS
→ DDR
```

因为：

> Core 0 的 X **还没搬完，也还没写入 Cache**。

结果：

```text
两核同时 MISS
```

而不是：

```text
一核 MISS
另一核 HIT
```

---

## 真正 Cache-friendly 的策略反而应该类似：

```text
Core 0:
COPY_IN(X)
──────完成──────>
       ↓ 写入 L2

Core 1:
          COPY_IN(X)
          ↓
         HIT
```

也就是说应该是：

# **近，但不能太近。**

更加准确地说是：

> **first-loader / leader miss + delayed followers**

要求 follower 的 COPY_IN：

\[
t_{\text{follower}}
>
t_{\text{leader finish}}
\]

同时还必须：

\[
t_{\text{follower}}
<
t_{\text{eviction}}
\]

所以真正要控制的是：

\[
t_{\text{load-complete}}
<
t_{\text{reuse}}
<
t_{\text{FIFO-evict}}
\]

而不是简单的：

\[
\phi(u)=\phi(v)
\]

“同波次”。

这一点如果不改，问题三甚至可能出现：

> 越努力让共享访问同步，Cache hit rate 反而越低。

这是一个非常值得我们后续利用的突破口。

---

# 七、它的 FIFO 模型还是稍微过于理想化

它用了：

\[
\sum size < 1MB
\]

之类的“波次工作集”来近似 Cache 是否能命中。fileciteturn0file1L231-L245

作为解析模型可以。

但真实 evaluator 是：

```text
FIFO
+
miss completion 后插入
+
hit 不改变 FIFO 顺序
+
多核同时共享带宽
+
并发 miss 完成时间不同
```

官方明确说明：

> 命中不会改变 FIFO 顺序；miss 完成后才插入；容量不足时按 FIFO 淘汰。fileciteturn0file0L400-L408

因此 Cache 状态其实是一个**事件驱动系统**。

只用：

```text
波次总量 < 1MB
```

无法准确推断 hit。

最终最好还是：

> 用官方 evaluator / 仿 evaluator 做 simulation-in-the-loop。

---

# 八、还有一些“看起来很高级，但论文里最好慎用”的表述

比如：

> “与寄存器分配 / Sethi–Ullman 问题同构”。fileciteturn0file1L151-L160

我觉得这里用词太满。

Sethi–Ullman 经典上解决的是树结构表达式的寄存器需求和求值顺序。

这里是：

- 一般 DAG；
- tensor size 不同；
- L1 / UB 双存储池；
- 多种 Pipe；
- sgid 约束；
- spill / reload；
- 多核依赖。

更稳妥的写法应该是：

> “与寄存器压力最小化、memory-aware topological ordering / peak live memory minimization 问题具有相似结构。”

而不是“同构”。

这种问题在国赛论文里不是致命错误，但**专家评委如果熟悉编译器，很容易抓出来。**

# 我现在对 A 题的看法反而比之前更乐观了一点

之前看题面，会觉得这是一个非常硬核的 NPU 调度题。

但现在仔细看官方附件设计，会发现：

> **真正硬件执行层已经被官方 evaluator 封装掉了。**

我们的决策变量实际只有：

```text
node → sgid

sgid → core

core 内 sgid order
```

剩下：

```text
Pipe 排布
缓存换入换出
DDR 带宽竞争
跨核同步
L2 FIFO
Makespan
```

全是官方帮你算。fileciteturn0file0L369-L377

所以 A 题真正可以做成：

# **组合优化 + 黑盒/半黑盒 evaluator 驱动搜索**

而不是非得成为昇腾 NPU 专家。

这其实和你昨天判断的“BCD 需要很深物理背景”不一样——**A 的硬件知识门槛没有表面上那么可怕，真正难的是搜索策略。**

如果让我现在给 A 题设计主线，我反而不会完全照这个售卖方案，而会走：

> **细粒度 DAG → 多级 coarse → 初始 partition → merge/split/move/swap 局部搜索 → 官方 evaluator 精确打分**

然后 P1/P2/P3 分别设计不同邻域。

尤其 **P3 的“首核预加载 + 其他核延迟复用”**，我觉得可能是一个比这份公开思路更有价值的切入点。
