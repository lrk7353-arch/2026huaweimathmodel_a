# 问题3 FIFO 与合法错峰调度的最小实验

本目录是**合成小图的机制核验**，不属于100个正式case的算法性能评测，不证明任何方法在正式数据上取得同等提升。运行未修改的官方 `evaluate_problem_3`，使用题目固定参数：2核、DDR 60 B/cycle、Cache 250 B/cycle、Cache 1048576 B、L1 524288 B、UB 131072 B、跨核延迟500 cycles。每组对照中保持原图和操作分核不变，只改变合法 `core_schedules` 顺序。没有插入人工等待、预取、虚构操作或调整评估器。

复现：在工作区根目录执行 `E题研究/.venv/bin/python A题研究/方案审阅/cache_order_microtests.py`。脚本仅使用标准库与本地官方模块。每例保存 `*_graph.json`、`*_plan.json`、完整 `*_result.json`，总表为 `summary.json`，官方源码与配置哈希见 `provenance.json`。

最小冷读图中，两个核心在t=0读取同一6000-byte输入，均miss。共享DDR后均在t=200完成，Cache才首次插入该输入。因此有共享输入不代表同步读取即可命中。

顺序对照图中，输入X、Y均为6000 B；X供核0和核1使用，Y仅供核1使用；三个计算输出均为60 B。核0的X计算与核1的Y计算均为10 cycles。短计算组中核1的X计算也是10 cycles，长计算组中仅此项变为3000 cycles。**长短两组不是同一输入图，组内两种方案才是严格对照。**

在先做Y的方案中，核0读X与核1读Y同时于t=200完成；两者均先插入Cache，再发射核1的X读取。因此核1在t=200即可命中X，独占Cache读仅需24 cycles。短计算makespan减少78 cycles；长计算却增加14 cycles。后者表明：减少DDR字节或提升命中率也可能推迟关键计算，损害最终makespan。只通过合法顺序实现的Leader–Follower方向成立，但必须权衡关键路径与Pipe重叠代价。

两组对照的 `data_movement_bytes` 均保持不变；这是在Cache模拟前统计的静态COPY量，不能拿它替代实际DDR访问量。`miss_bytes` 则从18000降至12000 B。

## 对分享方案两处公式的精化

1. **首读完成时间允许等号。** 在本评估器的retire-before-issue事件顺序下，首读完成并插入Cache的同一个cycle即可发射命中读取。本例 `t_leader_finish = t_follower_issue = 200`。更准确的条件是读取发射时Cache实际包含该逻辑tensor；单纯时间不等式仍不能替代同一时刻其他插入、淘汰的事件顺序。
2. **FIFO容量条件必须计入目标tensor自身大小。** 若x已插入，且D_x严格指此后直到访问前在x后面实际成功插入的其他条目总字节，则x未被淘汰的条件为 `s_x + D_x <= C`。`D_x < C` 不充分。例如C=1024 KiB，x=600 KiB，后续实际插入500 KiB时，D_x<C，但x必须被淘汰。命中访问不计D_x，已存在条目的重复插入尝试不计D_x，超过Cache容量而跳过的条目也不计D_x。若x被淘汰后再次插入，需从新的插入事件重新计算；不得按整段请求字节粗加。

精确代码依据：`multicore_cut_evaluate_problem_3.py` 第416–434行（FIFO插入），第487–510行（完成时插入），第539–581行（发射查找与带宽池），第583–590行（先retire后issue）。

这些实验没有证明“错峰总是好”或“问题3一定优于问题2”，仅证明特定机制与条件，正式算法应以官方makespan择优并保留不采用错峰的候选。
