## 一、真机与题目的对应边界

重新阅读了原始题目摘录（第006、014、018、025、040—060、077、083、097—102段）及入库官方config：

|项目|题目中的精确定义|真机实验应如何理解|
|---|---|---|
|输入图|Tensor只有id、pos、size；Op有id、op、pipe、cycles及依赖|没有完整dtype、shape、layout和数值语义，不能直接编译成等价神经网络；先复现依赖结构与读写关系|
|P1|每个子图一个Task；跨子图均经DDR；Task整体前驱约束与核内状态清空|用整批屏障、分阶段GM落地与分支局部推进作机制对照；不声称某次kernel launch就等于官方Task|
|P2|同核所有子图合为Task，复用该核私有L1/UB；跨核通过DDR和同步|研究生产者消费者的靠近、复用与并行的取舍；P2不是共享L1|
|P3|在P2上增加1MiB、250B/cycle共享只读FIFO L2|研究共享输入读序及复用窗口；不把真实L2当作同容量、同替换策略、同命中统计口径|
|计算资源|每个逻辑核有M、V、MTE2、MTE3，M/V可并行|Atlas A2为AIC/AIV分离架构；真实kernel的block数量与题目逻辑核不能直接等同|
|带宽与同步|DDR总带宽60B/cycle；P1跨核1000/同核100cycles；P2/P3跨核500cycles|不以测得的硬件带宽或启动延迟修改这些常数|
|片上存储|L1=512KiB、UB=128KiB；核内启发式可自动插入spill|CANN算子的显式buffer、tiling和真实资源限制不是这一自动spill模型|
|评估出口|输入方案只有node_to_subgraph和core_schedules|不会接收自定义预取指令、buffer数或自行改写后的算子；硬件启发必须转成合法划分、分核或顺序|

官方资料描述A2分离式AIC/AIV及其数据交换，见[Ascend C开发指南第4章](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/81RC1alpha002/devguide/opdevg/ascendcopdevg/CANN%E7%A4%BE%E5%8C%BA%E7%89%88%208.1.RC1.alpha002%20Ascend%20C%E7%AE%97%E5%AD%90%E5%BC%80%E5%8F%91%E6%8C%87%E5%8D%97%2001.pdf)。实际Buffer容量需根据产品确认；真实L2按cache line服务GM访问，具体与题目的只读FIFO模型不同，见[官方基础架构](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/Ascendcopdevg/atlas_ascendc_10_0008.html)。资料版本用于机制研究，不代表远端已安装对应版本。

## 二、优先实验：每个实验都要回答一个赛题问题

首批选择E1、E2、E3；环境和测量框架共用。E4—E6是后续扩展，不一次堆成大规模全组合搜索。

|实验|保持不变|主动改变|重点观测|能带回赛题的候选|
|---|---|---|---|---|
|E1 搬运与计算重叠|输入、输出、总工作量、数据类型|tile粒度、单/双buffer，受控计算强度|device时间、MTE/Vector忙碌及等待、有效带宽、buffer占用|按计算与搬运比、存活空间选择图粒度；找能让既有MTE与计算重叠的划分|
|E2 整体屏障与分支推进|同一批独立分支、数学结果、总算术工作|整批A后整批B；各分支A_i后B_i；必要时融合|关键链、并行时间、GM字节、同步等待；另列host启动开销|P1跨旧Task按依赖分支重划，减少人为整体等待|
|E3 共享输入访问顺序|每个消费者的计算量、消费者数、输入集合|共享输入邻近/分散访问，扫工作集及复用间隔|kernel时间、L2计数、主存读字节、关键消费者启动时刻|P3复用窗口与关键读优先；P2重复输入聚合|
|E4 复用与存活空间|计算及必要读写|生产消费距离、保留数据范围、分块/重载|片上需求、额外GM流量、时间|P2/P3仅融合可承受存活压力的区域，保留重载候选|
|E5 并发与带宽争用|总算术和总读写量|有效计算块并发、读写混合比例、分批时序|吞吐饱和点、各块尾延迟、总体时间|避免同时释放过多读写；按关键链与内存压力分配候选|
|E6 Cube/Vector互补|语义相同的矩阵和向量工作|阶段化、合法流水/混合实现|AIC/AIV利用率、数据交换代价|按M/V工作量与依赖互补分配计算分量|

E1优先从匹配工具链版本的官方Ascend C Add样例改造。DoubleBuffer本身只是一种真机实现；赛题不接受“设置buffer_num=2”，需要转译成划分与同核编排。官方说明其目标是让搬入、计算、搬出形成流水，见[DoubleBuffer与分块样例](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/910beta1/programug/Ascendcopdevg/docs/guide/%E7%AE%97%E5%AD%90%E5%AE%9E%E8%B7%B5%E5%8F%82%E8%80%83/SIMD%E7%AE%97%E5%AD%90%E5%AE%9E%E7%8E%B0/%E7%9F%A2%E9%87%8F%E7%BC%96%E7%A8%8B/%E5%A4%9A%E6%A0%B8-Tiling%E5%88%87%E5%88%86/%E5%B0%BE%E6%A0%B8-%E5%B0%BE%E5%9D%97.md)。

E2应拆开“依赖屏障”与“少启动几个kernel”的收益来源：第一组尽量保持实现和总流量一致、仅改变有效依赖；第二组才研究融合引起的流量变化。若只有启动开销下降，这个绝对数值不能替代题目固定Task延迟。

E3首轮用一个kernel内部多个块的共享只读输入，避免把Python框架优化误当L2收益；块的实际调度顺序不一定等于block编号顺序。若要控制到达次序，必须有相应时序证据。重复读取变快不足以单独证明命中率提升，计数器不可用时只能报告间接证据。

## 三、首个可执行批次

1. **环境确认。** 取得npu-smi、CANN/编译器版本、可见设备与可用profiling工具。环境清单成功仍不能算上板成功。
2. **官方样例上板。** 编译并运行匹配版本的Add，数值结果与参考对齐。之后确认一个最小profiling输出；不要先移植完整100图。
3. **E1小矩阵。** 3种合法tile粒度 × 2种buffer方案 × 2种计算强度，共12个实现配置；固定总数据量。先单块定位核内流水，再根据结果增加少量多块对照。
4. **E2/E3机制对照。** 各保留2—3种执行方式，并扫少量工作集或分支规模；先找机制是否发生，不追求铺满所有参数组合。
5. **回到题目。** 从P1 064/047的Task约束、P2 069类通信、P3共享输入类图中选相符区域，生成一条结构规则。这些图属于开发例；泛化验证另用冻结面板。case编号只用于选实验，不写进求解策略。
6. **交接另一研究分支。** 交付规则、特征、正负条件、硬件证据、题目中的可表达实现。由原官方评测决定是否进入统一算法。

12个实现配置是初始实验设计，不是性能收益或完成时间承诺。若只有框架级torch_npu可用，可先确认设备计算和粗粒度带宽/复用现象；细粒度流水机制仍需Ascend C或匹配的低层工具。

## 四、测量方式

- 先验证数值正确，再计时。检查优化前后数学工作一致，输出确实被消费；不要让编译器消去“模拟计算负载”。
- 分开记录编译、启动/host墙钟、device执行时间与数据拷贝。异步提交后明确同步，不能用Python函数返回时间代替设备时间。
- 建议先预热10次，再交错运行A/B、收集至少30个有效样本，报告中位数和波动；小kernel可批量重复并注明摊销方式。设备共享或波动较大时，这些样本不能支持小于噪声的收益结论。
- 无profiling的计时与带profiling的诊断分开运行；记录profiling回放次数与冷/热缓存条件。
- 开发并行可以加速编译；同一设备上的对照性能测量先顺序进行。主存饱和实验另按设计施加并发。
- 不宣称标准L2命中计数就是本题“可缓存COPY_IN命中字节/总字节”，两者分母不同。
- 不强制关闭硬件L2来伪造P2。若某版本有缓存提示API，也须注明其语义及支持范围。
- 真实上板结果、硬件仿真结果、题目Python模拟结果分别保存，不能混为一次实测。

官方工具支持区分上板的`msprof op`和仿真的`msprof op simulator`。前者可采集L2、Memory和管线利用率等；后者可提供指令流水图，具体可用项取决于版本/产品。见[工具使用与输出](https://www.hiascend.com/document/detail/en/canncommercial/800/devaids/optool/atlasopdev_16_00851.html)、[上板/仿真样例](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/80RC3alpha003/devaids/auxiliarydevtool/atlasopdev_16_0090.html)。不能拿仿真指令流水图称作真实芯片直接记录的逐指令时间线。

## 五、什么成果算值得带回

用“工作集/容量”“计算时间/搬运时间”“生产消费距离”“复用间隔”“可独立推进的分支数”表达规律。真机最优tile大小、真实同步延迟、替换策略和物理核数不直接写入赛题算法。

每条机制记录四项：

1. 观察到了什么，证据来自上板还是仿真；
2. 哪个控制变量导致差异，仍有哪些混杂因素；
3. 能否用原题允许的划分、分核、顺序表达；
4. 在官方固定参数下是否改善，在哪类结构上无效或变差。

只有硬件专属收益（布局转换、指令融合、特定cache hint、真实启动延迟）而没有合法赛题映射时，作为架构附录保留，不扩张成求解器新模块。本分支首轮目标是产生可证伪的机制假设，不能提前承诺质的飞跃。

## 六、环境检查入口与Git边界

`probe_environment.py`只查询npu-smi、命令位置、设备节点、版本元数据；不安装软件、不启动NPU计算、不修改环境。它输出JSON到标准输出。在远端运行：

```bash
python3 probe_environment.py
```

若只需最快反馈，先运行：

```bash
npu-smi info
command -v python3 bisheng ccec msprof
```

`command not found`还可能表示CANN环境未加载；不能据此认定平台没有设备。截图中的`ipconfig`是Windows命令，在Linux Bash里失败不影响NPU可用性，也不需要先查IP才能做上板实验。

本地隔离目录：`questionA/昇腾910B机制研究`。另一个对话的`统一算法迭代`工作树及`codex/memory-aware-research`分支不改动。原题config与官方评测器不修改；后续远端实验使用独立目录，不在cannbot源码中混入生成物。
