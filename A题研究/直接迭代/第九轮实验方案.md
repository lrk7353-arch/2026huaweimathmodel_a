# 第九轮：用当前官方轨迹分配后续搜索预算

起点为第八轮1500份方案。目标是解释并减少结构路线误判，在不增加单图调用上限的条件下兼顾WCC与后续精修。论文暂缓，不恢复旧长队列。

## 固定方法

新增`trace_routed`，保留原`staged/routed/component_wcc`行为和默认值。

1. 从原图开始，最多评测2个Component候选，再最多2个WCC候选。去重、失败、成功缓存与时间处理沿用原共享预算。
2. 对原结构规则选择staged的图，继续staged。对原结构规则选择Component/WCC的图，从本次前缀的最佳官方时间线计算`1 - 最大单核M或V忙碌周期 / 当前makespan`。
3. 该数值低于10%时进入staged；否则继续完整Component/WCC。没有成功前缀或时间线不完整时回退staged，允许Operation候选寻找可行解。
4. 准备切换时，从尚未评测的WCC交织候选中最多额外探测一个：优先最小化超出L1/UB容量的内存代理比例，再按计算结束时间代理排序，平手沿用原顺序。此探测正常占一次额度，无论成功、失败还是命中缓存；不足的时间/调用预算不会继续尝试。

10%是固定工程阈值，代理只用于候选排序。忙碌周期仅统计原始M/V计算；M/V区间以外的时间并不等于内存等待。该指标不考虑改变分核后的工作量，不是全局最优下界或可实现收益。容量代理不证明可行性，仍以官方评测为准。L1/UB峰值、spill及缓存统计记录为诊断信息，目前不直接决定主分支。

补充3图两场景均3胜0平0负；23张实际比较图合计，trace_routed对staged在P2为9胜14平0负，P3为10胜13平0负。保留分组统计及相对routed的负例，在此证据范围内将直接迭代CLI的P2/P3从头默认改为trace_routed，并将此模式默认预算从8次/180秒改为已比较的12次/120秒。显式参数仍优先；P1和warm默认不变。补CLI路由测试后总40项测试通过，并另作一次不指定方法或预算的全新缓存真实运行。此入口决定在比较结束后执行，未改变对照组的12次/120秒口径。
