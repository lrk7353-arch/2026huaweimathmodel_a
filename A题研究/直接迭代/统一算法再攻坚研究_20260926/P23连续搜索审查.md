# P2/P3 持续反馈与少量多父搜索：现状审查和可落地的闭环

审查范围：当前工作区的 `cold_portfolio.py`、`search_budget.py`、`refine_regions.py`、`p23_data_refine.py`、`p3_feedback.py`，并核对其调用的 `p23_region_refine.py`、`critical_wait_candidates.py` 和既有负例。仅阅读与制定设计，没有新增官方评测或修改公共代码。

## 判断

用户提出的“持续诊断瓶颈、修改相关区域、保留少数结构不同父方案”方向合理，但其中多数部件我们和队友已经实现过。不能把它包装成全新发明，也不能以换成beam或闭环名称推断会改善。

目前的缺口在于：**父方案、轨迹、区域候选和剩余执行机会没有被作为一个可持续的搜索状态来管理。** 新方案一旦成为best，旧路线虽然可能仍存在于字典或队列中，却会失去执行资格；部分联合动作在完成之前，又受当前裸方案时间的过滤。结果是局部探索不断换起点，难以完成有潜力的改动链。

下一步应复用已有等待诊断和联合操作，把这个状态管理问题补齐。w200+插空应保留为有效构造操作和回归证据，不继续把“再找一个漏掉的固定入口”当主要研究范式。

## 现有代码已经做到什么

|模块|已经实现|还没有保证|
|---|---|---|
|`cold_portfolio.py`|原图从头求解，统一预算；按(parent,family)保存局部队列；保留完整WCC来源；成功后下一次调用能读取新父轨迹|旧父离开best/beam后仍获执行机会；改善后持续重算操作族优先级；新旧队列公平推进|
|`search_budget.py`|真实的至多3个已付费官方父方案；结构去重；按访问次数、全局改善和秒数选择|父方案在完成一次联合修复前不被淘汰；同一分核的顺序变体不占满所有槽；一条暂未超过全局best的路线仍能完成有价值的后续|
|`refine_regions.py`|接受新解后立即刷新官方轨迹；保留旧pending；旧局部、区域、缓存候选的可比运行框架|旧pending不会被不断插到队首的新批次挤到预算外；有限预算内一定扩展不同结构父方案|
|`p23_data_refine.py`|精确核对pre-spill COPY字节；输入读者/区域/分量迁移；有界就绪窗口的存活时间排序|该文件中的迁移和排序已组成一个完整动作；选区来自真实关键等待；保留未改动区域的原编码|

所以，不能说当前只是“假beam”或“完全没有反馈”。更准确地说，是已经有这些机制，但其准入、执行和状态继承规则限制了效果。

## 代码对应的具体失效机制

### 1. 已保存的旧队列，仍可能永久不可达

`cold_portfolio.py:155—162` 用 `(parent_record, family)` 保存局部队列，旧队列不会自动清空。但默认模式在 `154` 只从当前best取父方案；budget模式在 `188` 从 `SearchBudget.choose()`取父方案。后者仅遍历当前beam，见`search_budget.py:41—48`。父方案被beam移除后，对应队列即使还在内存里，也没有后续入口。

`search_budget.py:28` 把比当前best慢5%以上的父方案排除。009清楚说明，当前裸时间不足以判断其后续价值：旧stable_w100父方案P2为77300，新的w200插空为46156；旧父一定越过5%门槛，却能经一次完整插空到42596。P3相应为74767、42009，而旧父直接插空38411。这里不是给差方案无限预算，而是**完整修复尚未试过就按中间状态淘汰了来源**。

此前009的第十三轮负例也相同：旧强基线第12调用才执行`cross_release_dependency_tail`到52200，beam只得到75349。第十三轮报告已经明确指出候选排队与小幅改善后重新生成的问题。今回新的早期w200也使009/P2 42596→45261、P3 37274→41281，再次展示同类问题。

### 2. 多个不同record不等于多种核心分配

`refine_regions.py:19—24` 的`structure(plan)`保存每核按顺序排列的Task成员。它消除了Task编号差异，但保留核内Task序列。在P2/P3原子Task编码下，同一核心归属、不同排序可以得到不同指纹，占用3个beam槽；核心标签置换也没有归一化。这是可用的“方案形状”比较，却不足以代表核心分配多样性。

`search_budget.py:25—35` 又按官方时间排序保留这些形状，使三个槽可能只覆盖一个分核附近的排序变体。应同时记录“核心归属/分区结构”和“顺序/编码”，前者用于控制父方案多样性，后者仍保留供调度搜索与精确去重。

### 3. 小幅改善重置了父记录访问历史

`search_budget.py:45` 用`visits[record_path]`选择父方案，`70`也按record记访问次数。一个略好的新record访问数从0开始，能再次优先扩展。`cold_portfolio.py:157—164`还为这个新record重新生成最多24项队列。旧路线的执行历史没有传给新状态。

这不只是“多试一轮”：同一结构的小改动可能不断获得新起点待遇，而其他分核或老队列的深层候选始终排不到。

### 4. warm闭环会刷新，但每次刷新可能抢占整个队首

`refine_regions.py:103—123` 从beam选父方案、生成24项邻域，并通过`pending.extendleft()`置于旧候选前；`147`发现任何词典序改善后立即退出当前批次并重新观测。这部分是真实闭环，不是静态重启。

但父方案每次变化都会带来新的一整批候选。旧尾部仍在，却没有最多等待多少调用的保证。`148`每8次尝试让出一次机会，也没有让队列里最老的父来源优先。warm版3%准入在`93`；旧beam成员不会像SearchBudget那样全部重新按margin过滤，但排序截断仍可能淘汰旧来源。

### 5. 所谓“当前瓶颈路由”并没有持续更新

`cold_portfolio.py:35—47`依据输入复制比例与spill排序data/region族；`91—93`只在起点算一次。成功后`215—217`仅在此前没有可行解、现在恢复可行时重新计算；正常改善不会重新决定族顺序。

区域生成器会读取新轨迹，因此不能说全部静态。问题是外层对哪种瓶颈优先的判断，多数时间停留在旧起点。

### 6. COPY、存活时间和分核曾并列，部分版本尚未联动

`p23_data_refine.py:149—151`核对pre-spill COPY，是很有价值的约束；它防止字节模型悄悄偏离官方语义。

但`162—167`生成“固定分核只改lifetime顺序”；`168—173`生成“迁移后仍用旧observed顺序”；`174`将二者交错排队。这份文件本身不是迁移与顺序的联合修复。`reuse_proposals()`虽收了timeline参数（99），实际选种子仍是复制字节和静态管线负载（104—123）。

不能据此推断我们从未实现联合：

- `p23_region_refine.py:96—116`已把迁移/交换分别与observed或tail顺序配对。
- `critical_wait_candidates.py:126—188`已用等待、slack、复用迁移、交换和pipeline/lifetime排序组成完整候选。
- 同文件`190—205`已有FIFO窗口与相关迁移联动。
- `residency_frontier.py`和本轮w200探针，也已验证迁移/分核与空隙插入的组合价值。

现成的联合动作应该复用。真正需要检查的是选区质量、区域外副作用和它们能否在预算内完成，而不是再增加一个同义模块。

### 7. P3反馈是两族有限更新，不是统一多父闭环

`p3_feedback.py:54`只有两个操作族队列，二者生成时均读取同一个best（62），没有独立父谱系。`78—79`把新读序批次放在队首、保留旧尾部；但`85`会主动清掉legacy第0轮剩余队列，以复刻旧方法的轮次宽度。

读序刷新需至少0.5%时间收益，且最多第二次生成，见`86—87`、`136—138`。它有保护另一操作族的饥饿规则（40—41），这点值得保留；然而这只能保护两个arm，不能保护旧父方案。

`search_budget.py:72—74`只奖励全局makespan改善，不奖励一个落后父方案的局部进步，也不奖励COPY改善。这样设计能约束最终时间目标，但在尚未完成联合修复时，可能又把有价值分支当作无收益来源。这里适合分开“最终输出选择”和“搜索状态继续保留”的准则。

## 收尾可落地的最小统一闭环

这是待实现设计，不声称已经超过现有主干。保留现有候选生成器与官方模拟器，只改状态组织，再给区域联合操作一个稳定执行入口。

### A. 三层状态，而不是一个best加若干候选名

```text
SearchState
  budget_used, deadline, exact_seen, official_best
  active_lineages[最多3个]
  completed_records + Pareto_archive

LineageState
  placement_signature          # P23核心归属；P1再含Task边界
  best_record_in_lineage         # 已付费官方方案
  observed_bottlenecks           # 该record的官方轨迹、关键等待摘要
  pending_actions               # 每项带原父record，不改写来源
  visits_total, last_served_call # 新子record继承访问历史
  committed_calls               # 尚欠的完整修复尝试，已从全局余额预留

Action
  parent_record, region_id, boundary_constraints
  joint_edit, alternative_edit, exact_plan_hash
  created_call, progress_cursor, evaluated_or_pending
```

`official_best`只用于保证最终输出；一个不同核心分配的搜索来源可以暂时落后。为每个新来源预留至多两次完整修复机会，完成以前不按“距best 3%/5%”丢弃；没有剩余配额就不接收新的待扩展来源。新增best始终保存，但不自动清掉其他谱系或重置访问数。

三个槽包括当前最好、一个核心归属不同的来源，以及第三个非支配/结构不同来源。选择以可计算的分核和分区指纹为依据，不能写case列表。不同顺序保存在同一分核谱系中；必要的不同COPY方案放在归档中，归档不等于免费额外搜索槽。

精确评测去重继续使用有序JSON，绝不拿核心标签或Task归一化后的结构指纹替代官方输入哈希。结构归一化只负责多样性。

### B. 每次只展开一个相关区域，完成联合动作再评分

从该父方案的官方编译后等待摘要选择当前关键等待附近的区域：计算重核、跨核COPY、内存复用依赖、关键读窗口。它是改动线索，不是假装拥有精确的反事实收益下界。

区域应包含真正相互影响的两端：生产者和消费者、迁出和迁入核心的补偿区、共享张量读者及其阻塞依赖。复用已有grow、等待观察和边界闭包；允许跨旧Task边界，P1不能只拆旧Task内部连续块。

每次生成一个完整动作和一个有意义的替代版本：

- P1：区域重划＋分核＋边界合法修复，保留不合并版本，合并是另一个完整候选。
- P2：相关区域迁移/交换＋插空重排；确有内存压力时在该区域做lifetime修复，不能要求迁移先单独胜出。
- P3：在P2完整动作上加入与关键读有关的读序修复；只有真实的读等待/淘汰证据才使用缓存动作。

区域外的核心归属与相对管线顺序应保护，并记录改动闭包。当前多处`_runs_plan`会重编码整图，不能直接把这种操作称为“只动局部”；若不能保持原有编码，就显式把它列为全局重编码候选并保留控制。

所有组合只评完整方案，中间迁移、拆分或重排不要求独立降时。代理只决定尝试次序；只有已证明适用于固定完整候选的必要下界可作硬剪枝。

### C. 连续轮转，保住已承诺的执行机会

保留总B24与总墙钟，初始构造最多使用6次，余下调用由同一循环管理。新的w200等原图构造作为构造器中的有效成员，初始方案不是按case检索；6次上限不是收益保证，若强起点构造需要调整，作为明示实验配置。

剩余预算先兑现已承诺的完整修复调用，再在三个活跃谱系中轮转。每谱系一轮最多评一个候选，之后让其他有待办的谱系得到机会；新best产生时只给该谱系追加一小批（最多两个）基于新轨迹的动作，不覆盖旧队列。旧候选保留自己的父record，不能偷偷换成新best。

若有约定两次但全局只余一次，禁止接收新谱系；要保留`剩余调用 >= 未兑现承诺之和`这个简单不变量。配额不是每个模块额外获两次，而是占用B24中的余额。失败和缓存命中照常计费；超过墙钟不再开新调用。无新收益时扩一个相关区域或尝试另一尺度，最多两层，不启动无限重启。

暂时落后分支若改善其自身时间、COPY或关键等待，可以替换该谱系的工作状态；最终输出仍按官方目标选最优。先用确定的有限轮转做清楚，再考虑收益/耗时自适应，避免当前记录级奖励和机器噪声重新造成饥饿。

### D. 每个评测结果都反馈，但不是每次都全局重开

新记录的诊断必须与它自身官方轨迹哈希绑定，不能借旧轨迹评价新父。每次成功评测都记录该动作实际改变了什么：关键链是否变短、重核尾部是否前移、COPY和spill是否上升、P3关键读是否真正提前。

只有获得该谱系的新工作状态才基于新轨迹生成后继；失败候选不能触发所有父方案重排。全局best改善也不取消其他已经承诺的完整动作。

## 为什么这比继续调几个入口更接近用户要求

它改变的是搜索的单位：由“选一个模块继续跑，best变化就换父”改为“维护少数结构来源，每个来源围绕其当前瓶颈完成一项联合改动，再决定其后续”。新增结构来源可被保留，但不会无限扩张；旧来源可以继续，但不会无期限占据调用。

这仍然使用有限的操作集合。任何可实现启发式都需要定义操作；区别在于区域由实际反馈决定、动作可组合、执行状态持续，不是把弱例编号映射到固定方案。

## 不能忽略的旧负例与收尾判定

1. 第十三轮beam相对greedy：P2为0胜7平1负，P3为2胜4平2负；相对强主干的P2均值更差。增加父数量本身没有获利证明。来源：`第十三轮成果/第十三轮结果.md:39—62`。
2. 009两次独立反例均显示，旧队列深层动作/旧父后续可能在新控制器里丢失。本次二次诊断只能说明旧父值得保护，不能把两次追加调用并到B24分数。
3. 090/P2旧联合实验：只改顺序242551、只改分核244971、联合237104，相对原241954改善；成熟精修却能到235842。联合是必要方向，不等于已超过强基线。来源：`三指标联合推进_20260926/执行结果.md:84`。
4. 单纯lifetime排序曾破坏已有M/V交织；FIFO目标优先级未超过编码/插空控制。新闭环不能把这些操作默认都视作高收益动作。

收尾阶段建议只实现上述状态管理与一个现有联合区域操作适配，不同时再加新种子族、复杂学习路由或扩大beam。用现有正负例作开发回归，再冻结规则做同B24比较；评价除时间/COPY/失败率外，必须列出每条谱系实际获评的后继数、已生成但未履约动作、父来源淘汰原因和总生成秒数。

只有在完整闭环确实优于成熟主干时才进入最终全量；若仍无稳定收益，保留已确定改善的原图构造和官方选优入口，交付成熟统一算法及结果，不再以“架构更完整”作为继续扩张的理由。
