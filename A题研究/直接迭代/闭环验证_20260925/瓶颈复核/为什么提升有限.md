# 为什么提升有限（2026-09-25追加复核）

**用户的判断基本准确：上一阶段主要改进验证体系和搜索控制，尚未形成显著更强的核心划分与分配算法。** 接受后刷新候选、统一记账和预留精修额度属于算法流程改动，但核心候选仍来自队友已有的方法。此前另有区域搜索原型，证据也尚不足以支持升级默认。累计精选成绩上升不能全部归因于新增闭环。

## 1. 先把贡献算清楚

- P1五核累计平均加速比本轮由3.587638729升至3.595249595，只增加0.007610866，相对约0.2121%。本轮新改善五核的只有002、069两图，100图平均会稀释局部收益；这并不掩盖控制器本身改善有限的事实。
- 002暖启动：第六轮78244，旧单轮64307，新闭环64296。相对第六轮17.8263%的降时中，大部分旧方法就能实现；闭环额外仅11周期，即0.017105%。
- 069暖启动：单轮16818，闭环16521，闭环额外降时1.765965%。
- 002从头12次：旧portfolio与预留额度单轮均78244，闭环67360，降时13.910332%。这是真实的算法流程收益，但6图只有这一图赢，不能外推。
- 043四核的新精选243378，原portfolio也能得到。它证明旧方法仍有可挖掘成果，不证明闭环更强。

因此，现阶段应称“验证可靠、少数实例有效的搜索流程改进”，不能称“统一算法取得显著提升”。这些数据也未做统计显著性论证。

## 2. 首要限制是候选质量，增加预算解决不了

暖启动闭环预算8：12配置实际逻辑调用62/96，10配置候选耗尽；预算12：65/144，12配置全部候选耗尽。逻辑调用包含每配置一次起点，候选实际评测分别50与53次；两次实验的最好结果相同。

也就是说，扩大允许预算几乎没有增加有效搜索。多数配置并非没来得及试，而是固定种子和相同生成器反复返回相同方案，或剩余方案不能改善。

当前Task生成器只有同核合并、按旧轨迹时长重分配，以及按操作数512/1024等阈值拆分。合并保持核心归属；拆分也保持核心归属。重分配保持子图划分，采用一个基于时长和任务依赖的列表调度。不断刷新这些操作，并没有引入新的划分依据或更强的核心分配搜索。

## 3. 联动仍不充分，但简单串联也不够

当前控制器只接受立即改善的完整方案。一旦拆分先增加搬运、同步或Task切换时间，就不会继续沿该拆分方案探索迁移；接受一个小改进后，又放弃旧父方案尚未评测的候选。这两个限制由代码直接支持，后者已有单元测试反例。但“存在限制”不等于“去掉限制一定涨分”。

为核实第一点，追加4次官方诊断：使用043四核在暖启动中被拒绝的两种拆分轨迹，再分别执行local/observed重分配。所有4次均为新官方调用，2工作线程，无失败或超时。结果如下：

| 候选 | 原父方案 | 拆分中间结果 | 再分配后 |
|---|---:|---:|---:|
| split1024 + local | 266766 | 266793 | 266793 |
| split1024 + observed | 266766 | 266793 | 266793 |
| split512 + local | 266766 | 266954 | 266954 |
| split512 + observed | 266766 | 266954 | 266953 |

再分配实际改变了605—665个计算操作的核心归属，效果仍几乎没有变化。这不是“代码没有执行迁移”，而是现有拆分位置与分配方法没有找到有效组合。更不能追上从头原portfolio已经得到的243378。

这次诊断是事后机制检查，复用了旧拆分轨迹，其历史成本不计入4次新增调用；不用于固定预算排名，也不证明所有复合候选都无效。原冻结验证的384次调用与结论保持原样，新增4次单独记账，总计388次。累计精选成绩未变。

## 4. 有些图接近计算工作下界，有些主要瓶颈尚未碰到

对非COPY的M/V计算工作求 `max(总M周期, 总V周期)/核数`，得到必要下界：

| 从头配置 | 当前时间 | M/V工作下界 | 下界/当前时间 |
|---|---:|---:|---:|
| 074/4 | 414388 | 394856 | 95.29% |
| 025/5 | 975282 | 940564.8 | 96.44% |
| 043/4 | 243378 | 129438 | 53.18% |
| 069/5 | 16818 | 3334.8 | 19.83% |

074与025即使忽略所有其他开销，剩余降时也至多约4.71%、3.56%，不宜期待巨大增益。043与069下界较松，只能说明这一证书不能证明接近最优，不能反过来把差距当作可实现收益。

当前P1五核最低加速的8图为051、047、048、075、085、064、056、068，均不在本轮六图面板中。051、047计算工作集中在一核；075、085有明显重核。这些才应进入研究开发的诊断组，但必须再判断并行依赖、切分通信代价和内存限制，不能直接推断能均分提速。冻结面板用于公平验证，不等于研发优先级；两者用途应明确。

另外，从头候选中的tensor路线在6图中有5图被代理阈值全部挡住，仅043有1个候选通过。`proxy <= 0.85 * 当前时间` 是启发式筛选，不是必要下界证明。目前不能判断它漏掉了多少好方案，但应在小诊断组保留少量被过滤候选做校准，避免一种候选长期没有机会接受官方检验。

## 5. 修正下一步重点

先前把双父队列列为首项，现在调整优先级：

1. **先研究更好的切分位置与核心分配。** 在低加速图中，用实际计算周期、生产消费关系、张量边界搬运和任务等待选择区域；避免只按512/1024个操作切块。探索块迁移、交换及保留局部结构的联合分配，同时保留原布局和不合并版本。完整组合才进入官方评分，中间步骤不要求单独获益。
2. **用低成本解释模型筛选完整候选。** 区分核心负载、必要计算链、Task同步/切换、共享DDR争用与内存限制。local时长和旧布局下的observed时长都只能作为估计，不能替代新布局的官方时间。优先验证模型能否选中明显更好的候选，再扩大搜索。
3. **队列与预算作为辅助。** 保留少量旧父候选，降低重复无效合并的优先级，校准tensor筛选。它们提高试验利用率，但不能替代新候选质量。
4. **看到核心算法的明确对照收益后，再冻结验证。** 开发集可针对瓶颈选图；晋级评测另用未参与调参的结构面板，与强原portfolio保持同起点/同预算/同官方评测。若仍无优势，保留负例并更换候选思路，不通过加调用或累计挑选包装提升。

队友的成果不应被低估：现有生成器已经实现了多数改善，且原portfolio在043上击败了暖启动邻域。我们的不足，是这一轮还没有在这个强基础上提供更有力的划分和分配机制。验证工作已足够支持转向算法研究，继续主要完善验证执行的边际价值很低。
