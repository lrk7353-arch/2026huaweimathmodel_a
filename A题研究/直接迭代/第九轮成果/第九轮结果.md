## 2. 新方法如何决策

原`routed`只看分量是否容易分给多个核心；它看不见已经执行出来的实际瓶颈。新方法沿用初始最多2个Component、2个WCC候选，然后读取**本次**最佳成功方案的官方时间线。

对原结构规则选择Component/WCC的图，计算：

```
排程余量 = 1 - 所有核心中最大的单条M或V管线忙碌周期 / 当前总周期
```

这里仅统计原始M/V计算区间，不将插入的COPY算子混入计算忙碌时间。

- 余量至少10%：继续完整Component/WCC搜索。
- 余量低于10%：准备进入staged后续流程，但先从未试的WCC交织候选中，至多挑一个探测。
- 原结构规则已经指向staged、初始没有成功方案或轨迹不完整：进入staged，允许Operation候选继续寻找可行解。

探测先比较“计算接触内存代理是否超出L1/UB容量”，再比较计算结束时间代理，平手保持原候选顺序。这个探测、初始评测、失败及缓存命中都占用同一个总调用预算。未用额度仍按原规则回流；不是把多个完整方法跑满后挑赢家。

10%是固定工程阈值，不是证明出来的最优阈值。排程余量忽略改变分核后的工作量；M/V区间之外的时间可能包含其他计算、搬运、依赖与空闲，不能统称“内存等待”。容量代理只能排序，最终可行性与得分仍由官方决定。实际spill、L1/UB峰值及缓存统计已保存为诊断，尚未直接驱动主分支选择。

## 3. 三个不同机制实例

**078：从改顺序转向改分配。** 初始4次评测后，P3周期为511,983，最忙M管线已占509,472周期，剩余排程空间不足0.5%。新策略转向算子分配、轨迹及缓存阶段，最终468,009；837个原始计算算子改变所属核心，最大单核管线忙碌量降至408,408。最后一次接受发生在第11调用的`advance_leader`缓存候选。过程中同时改变了分配、顺序与读取行为，不能把全部43,974周期收益归因于某一种缓存动作。原固定staged也能得到468,009，新选路追回的是旧routed放弃后续阶段造成的损失。

**095：转向后续之前保留一次交织机会。** 初始结果220,314，余量约2.24%；新策略在第5次调用选择窗口4候选，得到220,188，与上轮充分WCC搜索的最好结果相同。原充分搜索在第8次调用才遇到它。分核未变；这是候选顺序和预算分配的改进，不是新突破了095的历史成绩。

**074：代理探测确实找到了额外收益。** 新验证中，P3的staged在12次内为337,615，旧routed为328,133，新方法为326,680。新方法第5次探测的是`wcc_protected_interleave_v2_w2_complement_memory_tie`，该次即得到最终结果，后续没有继续改善。这为“切换前留一次有针对性的探测”提供了实例证据，但不是证明代理排序在所有图都有效。

078、095及004的详细当前前缀对照见[路线机制证据](路线机制证据.json)。083、090的大幅累计改善主要仍来自更充分的WCC候选覆盖，不能全部算成新选路器独有的贡献。

## 5. 默认入口与真实冷启动

实际比较覆盖23张图。合计相对staged：P2为9胜14平0负，P3为10胜13平0负；其中只有上表12张属于本轮新验证，其余属于开发或追加回归。

据此将直接迭代CLI的P2/P3从头默认改为`trace_routed`，并使用已验证的默认12调用、120秒软预算。原默认CLI为8次/180秒，此次入口预算变化明确公开；**比较实验的两侧一直都是12次/120秒**，没有靠给新方法更多调用获得表中优势。显式参数优先；P1及warm模式仍为8次/180秒，P3 warm仍用legacy。

在“中文题目”目录执行即可，无需历史最佳方案或历史评测目录：

```sh
python3 -B A题研究/直接迭代/solve.py --case 78 --problem 3 \
  --from-scratch --fresh-evaluations --out my_runs/p3_case78_trace_default
```

该默认命令已实际执行，12次全部新评测、约2.18秒，得到468,009周期。输出目录必须是新目录。若希望指定旧流程，加`--p23-method staged`；若希望完整搜索分量交织，加`--p23-method component_wcc`。

另外，004、078、095的P2/P3共6个配置全新缓存从原图求解，均12次新评测，全部与对照结果一致；单worker墙钟30.54秒，各配置约2.00—10.62秒。运行期间另有验证负载，因此不能据此比较算法纯运行速度。显式CLI模式另有一次3.85秒复跑，与默认2.18秒只是两次不同负载观测，不是代码加速倍数。较大的091三核求解约88—107秒，说明图规模仍影响程序耗时。

新验证72配置、2个worker约521.66秒，其中864逻辑调用、221次新官方评测；其余为成功缓存复用。这替代了全量长扫用于当前方法判断，但不说明所有图都能几秒求完。完整成本见[主要批次成本](主要批次成本.csv)，并行批次墙钟不能简单相加。
