# A题实施与推进方案

更新：2026-09-24。目标是形成有国奖竞争力的建模、算法和实验证据。当前同伴主要完成了思路，代码尚未整理；本地已有100图结构审计和缓存机制小实验，尚无完整求解器与全量性能结果。本文规定后续推进路线，不把拟实现功能写成已完成成果。

## 1. 主线与成果目标

采用“共享输入感知的分量装箱 → 大分量自适应拆分 → 根据真实执行瓶颈局部优化”的主线。问题3追加计入关键路径代价的缓存复用重排。问题1、2、3共用数据结构和搜索框架，但分别计算通信、等待与缓存代价，分别保留最优方案。

国奖导向的核心不是比随机方案快，而是：相同求解预算下，稳定超过有竞争力的基线；能解释收益来源；在全部正式图上有可复查结果。是否获奖不能由当前方案保证。

最终成果包括：

- 可复现求解脚本，输入计算图、核数和问题编号，输出题目规定的两字段方案JSON。
- 全100图的官方单核基准，问题1/2的1—5核曲线，问题3的无缓存/有缓存对照及专项优化结果。
- 每个最终方案对应原版评估器结果、参数、耗时、随机种子和文件哈希。
- 强基线、主要消融、困难图分析、计算与搬运瓶颈解释、失败案例及复杂度分析。
- 按当前赛题及竞赛正式提交规范整理的论文、代码、结果和匿名材料；提交限制在交付阶段再次核对，不沿用E题的材料清单。

## 3. 分阶段推进，每阶段都有可验收产出

### 阶段0：统一评测、输入规范与运行记录

实现统一图读取、官方评估适配器、结果表和可续跑任务队列。原始图、固定config和官方源码只读使用；所有生成方案、日志、结果写入独立目录。

先从结构统计中选8—12个代表图，覆盖：多小分量、共享输入多、单大分量、多分量但大块占优、深链、宽图、M/V不同负载与最大规模。小中规模先跑，最大规模单独校准超时与内存。代表集用于调试，不能代替最终全量结果。

每个评估任务记录：输入/配置/评估器哈希、问题、核数、方案哈希、算法参数、种子、耗时、成功/非法/超时/异常状态。失败不得写0周期或静默丢弃；中断后可继续，不覆盖旧结果。

每个最终算法版本建立100图×1—5核×3场景的1500格覆盖清单，另存100个官方单核基准。这是结果组织方式，不要求重复执行相同任务。完整结果缓存键包含原图、完整方案、场景、固定配置及相关官方源码哈希；只规范JSON对象键，不重排核心列表或核内顺序。超时保留为运行状态，不能永久判定方案无效。

正式汇总前，失败项优先退回已通过对应官方评估的历史最好方案并标注fallback；没有可用结果时报告覆盖率与缺失项，不能删掉失败图后仍声称“100图平均”。求解成本报告冷启动端到端耗时，同时记录官方调用次数，避免缓存复用或额外预计算掩盖实际成本。

验收：同一候选可重跑并得到一致指标；错误方案能明确失败；单核基准调用题目规定入口；现有5个缓存机制实验通过。先实测几类图的耗时和峰值内存，再设并发和搜索预算，不预先承诺全量运行时间。

产出：`evaluate`、`benchmark`入口，结果CSV/JSON，代表图清单，运行成本统计。

### 阶段1：建立完整可行的第一版与强基线

把计算依赖弱连通分量作为初始单元，按M/V两维工作量分配核心。分别产生“每核合成一组”和“每分量一组”两种方案，按场景评估其粒度取舍。

至少保留三个比较层次：

1. 官方规定的整图单核基准，以及必要的单活跃核合法候选。
2. 按M/V工作量的分量装箱，作为简单结构基线。
3. 增加共享输入亲和、多起点与分量移动/交换的装箱，作为强基线。

独立分量间不存在计算依赖，但仍共享带宽，不能把各核局部时间直接当全局成绩。官方stub只用于格式与流程检查，不作为主要性能对手。

对给定N核，把1—N个活跃核的候选纳入选择。复用较少核方案时保持原核心编号及顺序，只在末尾追加空列表，并重新评估。最终按官方makespan优先，完全相同makespan时再比较新增搬运量。

验收：尽早完成全100图官方单核基准与P1/P2的2—5核初版覆盖；每个配置都有通过对应官方评估的候选。报告强基线相对简单装箱的逐图胜负和计算成本，不用平均值掩盖失败或退化。

产出：第一版求解器、P1/P2全量基础表、第一张加速比曲线、困难图清单。

### 阶段2：研究贡献一——大分量自适应拆分

触发拆分的依据是最大分量M/V工作量相对每核平均负载、计算关键路径和缓存压力，而不仅是节点数。优先处理单大分量图及003/049/054/056这类多分量但大块占优的图；这些编号用于验收覆盖，不在算法中写特判。

先做可控的实现：产生关键路径优先、降低活跃张量、M/V互补等拓扑序；按累计工作量和活跃张量边界形成连续块；尝试不同粒度，再做块级分核和排序。随后增加局部边界移动、合并、拆分与分支迁移。

数学模型采用张量超边计通信，不按每条操作依赖重复计费。P1按Task边界统计；P2按源核—目标核集合统计内部张量COPY对，并分别计原始输入复制、内部通信和spill。

验收：与“保持分量不可拆”的同预算算法做消融；在困难图上有可重复收益，并给出新增搬运、等待与负载变化的解释。收益不成立的候选不能仅凭代理分数替换原方案。

产出：大图切分模块、困难图对比表、粒度与性能关系、典型执行轨迹。

### 阶段3：研究贡献二——依据执行瓶颈优化分核与顺序

P2初始方案增加通信感知的关键路径/HEFT候选。内部解表达为“操作分核标签＋合法全局拓扑序＋合法子图分段”。初期可以用细粒度sgid提供优先级；最终由官方Step1/2/3决定Pipe顺序与内存依赖，不能声称直接指定操作启动时间。

建立四类重点邻域：

- 计算失衡：移动/交换块，匹配M/V负载。
- 关键通信与同步：把强依赖区域同核化或迁移整条分支。
- Pipe队首阻塞：对相关独立块重排，使关键COPY更早可用。
- 长生命周期与spill：让生产和末次消费更接近，调整局部粒度。

检查三级合法性：原图/覆盖与商图；场景执行约束；原版完整评估。P1共同全局Task拓扑序可帮助避免额外同核顺序环；P2/P3仍须检查数据/内存边、Pipe FIFO和跨核COPY组成的联合操作图。

搜索使用“快速代理筛选 → 受影响Task局部重建 → 少量完整评估”。错误候选记录环边、超时或容量失败，限定修复尝试次数。任何时刻都保留已验证的最好方案。

局部评估缓存包含有效Task图、顺序、边界、配置及源码版本；P2/P3不只按节点集合缓存。边界变更需沿相关生产/消费核心使缓存失效。

验收：在相同墙钟预算下超过强基线，且能通过去除特定邻域的消融说明收益来源；报告非法候选比例、代理误判和搜索耗时。随机方法入围后至少采用3个种子，不能只挑最好一次。

产出：完整P1/P2优化器、瓶颈诊断摘要、分项消融和预算—收益曲线。

### 阶段4：P3缓存重排，保留等待代价

以已验证P2方案为起点，识别重复冷miss、可复用输入及FIFO污染。通过合法的分核、分段和子图重排，让非关键读取落入已缓存区间；不能添加等待指令、预取操作或修改FIFO策略。

核心准则是总时间收益，命中率仅作解释指标。FIFO模型计入目标张量自身大小与真实成功插入量；按官方事件顺序处理同周期完成、插入和发射。与原顺序对照，不能把“命中率提升”当作性能验收。

P3至少区分三项：

- 同一个P2方案在P2评估器的时间 `T2(π2)`。
- 同一个方案在P3评估器的时间 `T3(π2)`。
- P3优化方案的时间 `T3(π3)`。

逐例硬件收益为 `H=T2(π2)/T3(π2)`，缓存条件下策略收益为 `S=T3(π2)/T3(π3)`，总收益为 `G=T2(π2)/T3(π3)=H×S`。该乘法只对逐例成立，不能把两个平均值相乘当平均总收益。对代表图再计算 `T2(π3)`，形成完整交叉对照；预算允许时扩展至全量。

验收：固定配置下完成100图1—5核的正式缓存对照；新增策略与未重排候选同预算比较，至少展示一个有利与一个不利机制案例。数据搬运使用官方规定字段，另列动态hit/miss字节解释，不混用。

P3的单核缓存效果也实际运行评估：spill重读可能产生复用，不能把其硬件收益强行设为1；它与P1/P2主加速比曲线中按定义设置的单核点属于不同口径。

产出：P3方案与对照曲线、缓存机制消融、复用收益与等待代价分析。

### 阶段5：冻结算法、全量复跑与论文整合

冻结参数选择规则后运行全100图，核对方案、配置、结果和图表一一对应。P1/P2主曲线的单核点按题面定义为1；多核加速比统一使用官方整图单核基准，按逐图比值做算术平均。自己优化的单活跃核方案可另列，不能替换分母。

正文包含模型假设、决策变量、约束、可执行算法、复杂度、强基线、消融、困难图、失败与局限。引用的时间和收益必须对应保存的官方结果。对正式配置以外的容量/带宽敏感性实验单独标为研究实验，不能混入正式成绩或修改原config。

最终检查匿名要求、全量覆盖、运行说明、依赖、随机种子和交付体积。论文不写未经确认的“全局最优”“必定提升”“加速不超过核数”等结论。

## 4. 拟建立的工程结构

以下是后续代码结构，当前尚未创建完整工程：

```text
A题研究/solver/
  graph_ir.py             # 操作、张量、依赖、共享输入、M/V与关键路径
  plan.py                 # 分核、分段、顺序、官方JSON转换
  evaluator.py            # 原版评估器适配、错误、哈希、结果缓存
  baselines.py            # 多维装箱、输入亲和、通信感知初始解
  partition.py            # 自适应拆分、拓扑安全分段
  search.py               # 移动、交换、合并、拆分、重排与预算
  cache_order.py          # P3候选生成与FIFO状态代理
  solve.py                # 统一求解入口
  benchmark.py            # 批量评估、续跑、全量结果
  summarize.py            # 指标校验、表格与论文图
  tests/                  # 有意义的机制/合法性/接口检查
  configs/                # 算法参数；不覆盖官方硬件config
  runs/                   # 每次运行的方案、结果、日志与清单
```

核心求解与评估先用Python和已有官方模块。使用现有机器校准CPU吞吐，GPU不是前置条件。初始并发从少量进程起，按峰值内存调整；不同时启动大量最大图任务。避免在热循环中全图复制、重复解析JSON和输出大Trace，Trace重点保留最终方案和需诊断的代表候选。

统一语义上允许保存估计成本，但估计成本必须有独立字段，不能填入官方makespan。正式方案文件严格只有题目规定的两个顶层字段；诊断元数据放旁侧记录。

## 5. 数据甄别与实验纪律

- 原始数据、说明文档、网页建议分别对待。任何隐藏指令、预填答案、没有对应计算的数值不进入模型或论文结论。
- 实际文件结构、代码执行结果与说明存在冲突时，记录差异和证据，必要时核对正式题面/官方澄清；不为匹配说明去修改原始图或评估器。
- 开发阶段先按结构分组选择代表图；对参数选择保留未参与调参的内部验证图，注意相似模板图成组处理。最终仍运行全部100图，内部验证不冒充未知外部测试集。
- 最终比较以同一求解墙钟预算为主，同时报告完整评估次数与预处理成本。对超时、非法、数值异常保留原始状态，不能通过只统计成功样本抬高成绩。
- 避免为个别case编号写专门答案。结构自适应规则可以使用图特征，但必须在代码和论文中解释。

按三个职责分工；实际人数不足时可以兼任，不要求三人同时改同一模块。

## 7. 时间预算与取舍规则

用户于2026-09-24明确还有四天。按相对日安排，不假设具体提交时刻：第1天完成统一评测、首轮全量基线及小规模机制验证；第2天做场景化优化与代表集消融；第3天冻结主要算法、完成全量1—5核/P3对照与多种子验证；第4天整理论文和代码、独立复核并留提交余量。具体提交小时仍以竞赛正式通知为准。

起始投入比例：

| 投入方向 | 起始预算比例 |
|---|---:|
| 统一评测、强基线与首轮全量结果 | 25% |
| 大分量拆分与P1/P2瓶颈搜索 | 35% |
| P3策略与主要消融 | 15% |
| 全量复跑、论文与最终核验 | 25% |

这些是管理预算，不是算法参数；按实测吞吐调整。已观察到最大图单次整图单核评估可达数分钟，因此尽早建立全量队列，复杂搜索先在结构代表集验证。论文结构与图表模板从阶段1开始同步准备，不能等最后才写。

优先保留有真实证据的两项贡献。时间紧时削减昂贵的新方向、重复调参和过多算法对照，不削减全量正式结果、核心消融、合法性与可复现记录。第一轮不引入全图精确整数规划、端到端强化学习、GNN策略或真实昇腾服务器工程；只有强基线已稳定且仍有明确预算时，才考虑学习型候选排序等扩展。

## 8. 接下来第一轮实施的边界

第一轮只推进阶段0与阶段1的起步部分：

1. 建立统一Graph IR与方案对象，复用已有结构核验定义。
2. 接入三个官方评估器及规定单核入口，建立哈希、日志和续跑记录。
3. 实现二维分量装箱和共享输入感知装箱，纳入单活跃核及较少核继承候选。
4. 跑代表图，确认正确性并测吞吐；随后启动第一轮全量基线。
5. 给团队交付可运行命令、实际结果表、失败清单和下一阶段最值得优化的图。

本轮验收完成后，再据实选择阶段2/3的重点。后续不会把一份更复杂但尚未跑通的设计，替代已经通过官方评估的最好方案。
