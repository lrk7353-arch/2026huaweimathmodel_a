# P2/P3 保优精修入口

`refine.py` 从明确提供的方案继续搜索。它属于正式 v2 之后的额外预算层，不修改正式方法、评估器、机器参数或已有实验结果，也不自动查找某个图的历史最优方案。

主要变化是保留最优可行解并继续轮换邻域。一次无改善，甚至一轮所有候选都重复，都不能说明下一轮没有机会；停止由调用预算、阶段预算和固定轮数控制。beam 六图探索在相同逻辑调用前缀没有胜出，而保优单路径在四图出现停滞后再改善，因此此入口不默认扩大 beam。

## 调用

```sh
python3 -B A题研究/精修求解器/refine.py \
  选题分析/A题附件/data/case_071.json -n 5 -p 3 \
  --incumbent-plan 已有可行方案.json \
  --run-dir 新的运行目录 \
  --trace-cap 30 --cache-cap 18 --round-width 6 \
  --max-rounds 5 --max-evaluations 49 --seed 17 --timeout 60
```

输入图、核数、问题、初始方案和新运行目录是必填项。核数支持 1–5，问题只支持 2、3。可选 `--config`，默认使用图所在目录的 `config.txt`；所有官方配置值必须保持原值。可选 `--evaluation-dir` 复用现有 exact-plan cache；命中缓存仍占一次逻辑调用，因此这里不作冷启动墙时比较。

默认值即上例。`--run-dir` 必须尚不存在，连已存在空目录也拒绝；程序不覆盖、自动续跑或清理既有证据。输出固定在运行目录，不提供会覆盖输入的 `-o`。相同参数重复实验请使用新目录。输入、配置、初始方案、源文件的 resolve 路径与输出交叉检查，拒绝官方附件目录内写入及缓存关键写入路径的 symlink。

## 搜索语义

1. 在所请求的 P2/P3 下重新官方评估初始方案，作为第 1 次逻辑调用。初始失败时终止，不把输入直接当作有效 best。
2. 每轮先 trace，再在 P3 执行 cache；每阶段从调用当时最新 best 的官方结果重新生成。P2 的有效 cache cap 固定为 0。
3. 每阶段最多提出 `round-width` 个候选，并受该阶段剩余额度和总剩余额度限制。对方案的精确 JSON 内容散列去重，保留字典插入顺序；不同输入顺序不能未经证明当成同一方案。
4. 已成功、已失败的同一方案都进入去重集合。重复候选不调用、不计费，但该轮被完整记录，后续继续增加 `round_index` 轮换算子。阶段 cap 计算实际预留的调用数，不计算重复或结构不合法的提案。
5. 所有候选先检查原操作覆盖及子图/核心次序合并无环，随后交官方判断真实执行图、FIFO、容量及性能。只有官方 success 且 `(makespan, added_copy_bytes)` 严格词典序改善才能更新 best。相同耗时更少复制字节仅是次指标改善。

默认 P3 最大 49 次 = 初始 1 + trace 30 + cache 18；默认 P2 最多 31 次。重复、候选池不足等会使实际次数更少。每轮的提案宽度不是“不断生成直到找到这么多个未见候选”；这一点避免隐藏额外生成搜索。上限并不表示保证用满，也不表示不同图/方法实际消耗相同。

trace 邻域包含末端/等待较高通信的单点或短链迁移、负载热点移动/交换、保持分核的优先序重排；它们是可解释候选特征，不是含所有内存动态边的精确关键路径。cache 邻域来自 P3 的真实缓存事件与顺序，含重编码对照。生成器诊断和 candidate metadata 原样留存，不能把重编码控制收益自动归因于缓存策略。

## 可中断审计与产物

- `manifest.json`：输入、初始方案、配置和明确依赖源码的 SHA256，全部预算、参数及计费规则。只加入 `refine.py` 自身及借用的明确依赖，不 glob 此目录其他开发文件。
- `trials/NNNN.plan.json`、`trials/NNNN.json`：每次调用前先写计划与 pending 记录，再原子更新 checkpoint，之后才调用评估器。返回后记录成功、失败、缓存命中或证据校验错误。
- `checkpoint.json`：任何已预留调用都可追溯。硬中断可能留下 pending；它按一次逻辑调用保守计费，但不能声称已确定启动/完成了 worker。
- `generation/`：每轮全部生成候选、诊断与生成父方案哈希；评估行另存调用前 incumbent 哈希，避免把同一批兄弟误记成父子。
- `best.plan.json`、`summary.json`：最后经官方验证的最优计划及完整评估、轮次、重复、生成失败、拒绝记录、停止原因和耗时。`completed` 与有可行结果分开。

成功记录必须同时匹配当前图、配置、问题、精确计划、官方源码、wrapper/worker 源码和 gzip 文件 SHA；原始结果的核数、makespan 和 added bytes 也必须一致。每轮重读当前 best 的官方证据，结束前再次校验源码、输入和 best。发现证据或源码变化时终止，并将留存 best 标为仅供审计，不报告搜索完整成功。

这里的 `--timeout` 只限制单次官方 worker；没有整体硬墙时监督器或自动恢复功能。需要进程级截止时可由调用方管理进程组，但终止后应按 pending 状态保留未知调用，不能把该目录当成 completed。

## 验证范围

`python3 -B A题研究/精修求解器/test_refine.py`：16 项机制测试通过，不调用官方评估器。覆盖停滞/重复轮后改善、失败不替换 best、初始复评及预算 1、缓存计费、pending 中断、阶段 cap、父子关系、损坏/非有限结果、路径保护，以及实际 trace/cache 生成器对 P2/P3 与 1–5 核的合成结构兼容。

真实 CLI smoke 在 `runs/refine_smoke_v1/`，运行前冻结 manifest、同一明确提供的 case071 起点、单 worker，最多 14 次逻辑调用；实际共 10 次，全 success，无生成失败，没有缓存命中。

|问题|初始复评 makespan|最后 makespan|added bytes|实际调用|结论|
|---|---:|---:|---:|---:|---|
|P2 / 5 核|9211|9211|361586|4|保留初始方案；三轮均执行，最后一轮全重复|
|P3 / 5 核|7797|7502|361586|6|降低 3.78%；赢家为 `cache_reencode_control`|

P3 的收益是官方验证的方案变化，但这个 smoke 不能证明缓存专用算子收益，更不是全量或同预算胜率。P2 不改善的结果与所有候选均保留。初始方案来自早前开发实验，故此 smoke 只是入口与机制验证，不属于独立测试集。
