# 用现有冻结入口做短迭代：代码核验与参数

这是快速筛选配置，不是新的正式算法版本。此次只读核验代码与已有结构统计，没有新官方评估、没有修改冻结源码。快速筛选不能代替最终全量、留出图验证或公平对照。

## 可直接使用的预算

共同条件：先选择同一图、同一核数、相同问题已验证的 incumbent；每个 run-dir 必须从未存在，输出不能覆盖 incumbent。保留初始计划复评，允许 `--evaluation-dir` 指向既有 exact-plan cache。缓存命中仍收费，不能作为冷启动速度证据。

|问题|推荐入口|初始复评|候选阶段|每轮宽度 / 最大轮数|总调用上限|
|---|---|---:|---|---:|---:|
|P1|solve.py|1|selective ≤8，其他阶段全 0|4 / 1（P1 不迭代）|9|
|P2|refine.py|1|trace ≤8，cache 0|4 / 3|9|
|P3|refine.py|1|trace ≤4，cache ≤7|4 / 3|12|

上限不是必定消耗：内部 exact 去重、生成量不足、P1 严格下界剪枝都可能减少实际调用。失败、超时和 exact-cache hit 都占一次；未返回 pending 也已经预留预算。建议小图首轮 `--timeout 20`，只筛选运行开销可控的结构面板；超时不能解读为算法无效。候选超时后仍保留此前已验真的最优计划。

P1 的限制必须说清：当前 selective 接口只接收 graph/N/cap/seed，**不接收 incumbent**，它重新生成固定结构候选池。incumbent 只参与保优和严格计算/Task 下界剪枝。这是“用强基准筛选候选”，不是围绕 incumbent 迁移/合并 Task 的真正局部搜索。如果该起点已经完成同一 selective 候选前缀，这组命令主要会重看旧方案，应先排重，不要反复运行。

下面是可复制的 shell 函数；参数依次为图、核数、已验证计划、全新运行目录、评估缓存目录。函数定义本身不运行评估，显式调用时才执行。路径中空格和中文已加引号。

```sh
quick_p1() {
  python3 -B 'A题研究/精修求解器/solve.py' "$1" -n "$2" -p 1 \
    --incumbent-plan "$3" --run-dir "$4" --evaluation-dir "$5" \
    --component-cap 0 --operation-cap 0 --selective-cap 8 \
    --wcc-cap 0 --trace-cap 0 --cache-cap 0 \
    --round-width 4 --max-rounds 1 --max-evaluations 9 --seed 17 --timeout 20
}
quick_p2() {
  python3 -B 'A题研究/精修求解器/refine.py' "$1" -n "$2" -p 2 \
    --incumbent-plan "$3" --run-dir "$4" --evaluation-dir "$5" \
    --trace-cap 8 --cache-cap 0 --round-width 4 --max-rounds 3 \
    --max-evaluations 9 --seed 17 --timeout 20
}
quick_p3() {
  python3 -B 'A题研究/精修求解器/refine.py' "$1" -n "$2" -p 3 \
    --incumbent-plan "$3" --run-dir "$4" --evaluation-dir "$5" \
    --trace-cap 4 --cache-cap 7 --round-width 4 --max-rounds 3 \
    --max-evaluations 12 --seed 17 --timeout 20
}
```

这些函数从中文题目工作目录运行。需要自定义 config 时补 `--config 路径`；省略时按原图同目录的 `config.txt`。以上 cap / 参数已用两个真实 parser 解析检查，但没有实例化求解器或启动评估。

如果必须统一到 v3 `solve.py` 及其更完整 `verify_summary` 证据链，P2/P3 也可使用同一数值，并显式补 `--component-cap 0 --operation-cap 0 --selective-cap 0 --wcc-cap 0`。初始复评成功后，两条路径都跳过基线/操作阶段；差别是 **refine 初始失败立即停止，solve 初始失败还可能调用单活跃核 fallback**，因此后者不能宣称严格 incumbent-only。总预算仍不会超过设置。

想专门测试 WCC 时，另立一组 P2/P3 实验：solve、incumbent、component/op/selective/trace/cache 全 0，`--wcc-cap 8 --wcc-policy mixed --max-evaluations 9`。不把 WCC 插进 9 调用的 trace 筛选后再宣称两者获得相同局部邻域预算。

## 轮换与排重的真实行为

`controller.py:456–479`：初始复评→component→必要 fallback→selective 或 operation→WCC→逐轮 trace/cache。零 cap 在 `stage` 入口就返回，不生成该阶段候选（403–407）。有 incumbent 并不会自动关闭默认 component6 / operation12，必须显式设 0。

`refine.py:305–324`：初始方案必须在本问题重新通过官方评估，然后按 trace→cache 顺序迭代；不会因一轮无改善或全部重复而停止。`max_rounds=3` 包括索引 0、1、2。每轮基于当前最优计划重新取官方轨迹；同一批生成的候选仍来自生成时的父计划，不会在批中每次改善后立刻重生成。

轮换是真实的：trace 通信按轮次交替 late / high-wait 排序，并轮换 producer_single / consumer_single / producer_chain / consumer_chain；优先序在三种顺序间轮换（trace_refine.py:230–250、313–325）。cache 按轮次转移目标 tensor、改变提前距离（cache_refine.py:303–313、356）。但 cap 到达后该阶段不再生成，因此“最多三轮”不保证每个算子都被评估。

建议宽度 4 的原因：trace 可能先生成一份重编码 control，再依 communication、load、priority 轮转（389–402）；宽度 1–2 常被 control 和第一族占完，无法代表完整邻域。cache 也总先放 `cache_reencode_control`（339）。control 若与历史方案相同，控制器会跳过官方调用，但这份 control 仍占本次 generator 返回配额；小剩余 cap 可能因此花不满。这是现有接口的限制，不能把“没有更多调用”说成不存在改进空间。

排重分三层：

1. 同一 run 内，按保留 mapping 插入顺序的精确计划 hash 去重；不得排序 JSON 键冒充等价，顺序会影响官方行为。
2. 跨 run，`--evaluation-dir` 可省实际重算，但 cache hit 仍占逻辑预算；现有 CLI 没有历史 seen-list 或 round-start 参数。只把 best 传给下一次 CLI 会从 round0 重新开始，不是断点继续。
3. 真正试新算子前，纯生成并把候选 exact hash 与已保存 trials/hash ledger 比较；只统计新计划数、结构族覆盖，再决定是否实测。若要自动排除历史候选并从 round3 继续，需要另写独立实验控制器维护 seen/round 状态，不能声称现有 CLI 已支持。

seed 的限制只针对这里的固定生成器/相同起点，不能推断完整 v2/v3 无效：

- P1 selective 的 seed 只按奇偶轮转 local_quantile/phase_band 两族，17/29/43 都为奇数，相同输入和 cap 得到相同前缀（p1_selective.py:265–268）。改 seed 不产生新的 Task 切法。
- 对固定 plan、官方轨迹和 round_index，trace 通信的 seed 只控制前至多 4 个目标的 `seed % head` 轮转，因此 17 与 29 差 12，生成顺序相同；load/priority 不使用 seed。完整组合搜索中的 component/operation 可能改变起点，不属于这个结论。

## 小图结构面板

先固定结构层，不按本次算法是否改善挑图。现有原图审计表 `方案审阅/结构核验/a_graph_structure.csv` 可支持以下第一轮面板（全部 ≤1416 compute op）：

|结构作用|图|compute op|真正依赖 WCC|补充特征|
|---|---|---:|---:|---|
|多小分量、共享输入|001|600|200|一个根输入共享到 200 个 WCC|
|多小分量、无跨分量输入共享|008|864|108|8 层，原始 COPY_IN 约 1.99 MB|
|单 WCC、M/V 混合、宽并行|071|741|1|46 层，最大层宽 100|
|单 WCC、较深依赖|064|906|1|123 层，最大层宽 32|
|单 WCC、纯 V|051|1416|1|192 层，V 总工作 607080|
|多个深分量、共享 DDR 输入|044|1364|11|124 层，50 个跨 WCC 共享输入|

一般新 trace 算子先用 071/064/051；WCC 新算子先用 001/008；P3 cache 先用 001/008/044，并从**当前 incumbent 的官方 P3 轨迹**核对 repeated reads / inflight miss / eviction 类型。原始输入超过 1MiB 不等于实际一定驱逐，图结构标签不能替代当前轨迹诊断。首次只固定 N5，第二轮补 N2 验证活跃核和通信取舍，避免一开始扫所有核数。

有潜力后按预定顺序扩充：保留同族未用图，例如 093（多小 WCC）、019（混合规模）、069（单 WCC 宽层）、049/082（较大重 WCC）。这些图已有开发历史，因此仍是开发面板，不能称为未经调参的统计留出集。最终需要另固定未据本次结果挑选的验证图及全100图对照。P1 的 003/016 大图及大量 Task 方案不宜放在每次代码修改的首轮：先过覆盖/商图和必要计算/DDR下界检查，再预注册较长单调用。

判读时同时报告：新唯一候选数、各族实际调用、调用失败/超时、baseline 是否 exact-cache hit、最好时间和新增字节、全量预算及耗时。起点已经强且没有改善是有效筛选结果；只有缓存命中旧候选、control 重编码或时间预算未实际覆盖邻域，不能据此判定新方向无效。P3 的 control 收益也不能当成 cache 机制的因果收益。

## Timebox 的接口边界

当前两个入口都**没有总 wall-budget，也没有候选边界 deadline**。`--timeout` 仅限制每次官方 worker（solve.py:30，controller.py:188–200、380；refine.py:104、239）。调用数×timeout 也不是严格总墙时上限：纯生成、哈希、压缩、验真和 IO 不受这个乘积限制。

旧 `advanced_solver/supervisor.py` 不可直接套给 v3：它导入旧 CLI parser、固定启动同目录旧 solve，并按旧 engine 的 source closure/schema 恢复。可以在**新独立 adapter**中复用它的 `supervise(command, seconds, log_path)` 进程组硬截止原语，但不能复用旧 main/recover；超时后必须标 `completed=false`，有可验证 best 也只代表有可行部分结果。

如果需要温和的候选边界 timebox，需在新的实验 runner 加 `deadline`：生成前、每次候选评估前和返回后检查；到期不再开下一候选，保留已验真 best、已用调用和完整 pending/returned 证据。每次评估仍有单调用 timeout。纯候选边界检查不是硬墙时上限，可能超过 deadline 一个已启动调用与生成/验真耗时；要硬上限再叠加进程组 supervisor。外部轮询 checkpoint 不能无竞态地保证恰好停在边界。

恢复时不要直接把运行中 checkpoint 交给 `verify_summary(require_completed=False)` 当通用恢复器：它有 best 时仍要求最终 output/output_sha256，checkpoint 通常尚无这些字段。pending trial 的落盘早于 checkpoint，returned trial 也可能比 checkpoint 先一笔（controller.py:376–377、398–399）。新 adapter 需检查连续 trial 记录、保守计已预留调用，并对保留 best 用原 `Solver.verify_success` 的只读 view 验真；不能自动重跑不确定 pending 或把硬中断当正常完成。
